# Agent Loops

Run a task loop across several CLI coding agents using a hybrid orchestrator model.

```text
               +-------------------------------------------------+
               |                  Orchestrator                   |
               | (decides next action: worker, reviewer, finish) |
               +-------------------------------------------------+
                                       ^
                                       | action / result
                                       v
               +-------------------------------------------------+
               |              Deterministic Runtime              |
               | (enforces step budget, timeout, read-only check)|
               +-------------------------------------------------+
                               /                 \
                              /                   \
                             v                     v
                 +-------------------+     +-------------------+
                 |      Worker       |     |     Reviewer      |
                 | (modifies / tests)|     |    (read-only)    |
                 +-------------------+     +-------------------+
```

An LLM orchestrator directs the task by choosing discrete structured actions, while a deterministic Node.js runtime enforces safety invariants, step budgets, process lifecycles, and mutation boundaries.

## Architecture

- **Orchestrator**: Evaluates task status, worker findings, or reviewer feedback, and returns a validated JSON action (`run_worker`, `run_reviewer`, `finish`, `abort`). It never edits files or executes subshells directly, with one exception: on a run that ends with `--require-ci`, it may read the pull request check status with `agent-loop role wait-checks`, and that status read is the only command the exception covers.
- **Worker**: Executes the task, modifies files, and runs validation commands in the target repository.
- **Reviewer**: Evaluates the repository state and tests in read-only mode.
- **Deterministic runtime**:
  - Enforces step limits (`--max-steps`, default 20) and timeout boundaries.
  - Spawns agents, manages persistent sessions, and captures process signals (`Ctrl+C` exits 130).
  - Enforces non-mutating safety on reviewer and orchestrator turns using CLI flags and pre/post Git work-tree mutation detection.
  - Recovers from malformed JSON via a single repair turn.
  - Enforces the completion rule with `--require-accept`: after a worker turn, a `finish` needs a later reviewer `verdict: accept` with a `Checks` line on that state; with no worker turn, it needs at least one reviewer report. A `--mode review-only` run refuses the flag and applies the reviewer turn with no flag of its own: the interactive path reaches it because its init dispatch is the reviewer turn, and the headless path refuses a finish until a reviewer turn has run, whatever that turn returned. The gate is on that dispatched turn, not on a report, an accept, or a readable verdict. The gate follows turn order only, so an edit made outside the loop after the accept is not detected.
  - Resolves the PR head in the runtime with `--require-ci <pr>`, the same gate the interactive `role finish` uses, so a headless PR run no longer depends on the parent reporting the compare. It refuses a finish that also sets `unresolvedCompare`, and it reads the reviewed state of the last reviewer turn, so a worker turn after that review refuses the finish.
  - Declares a run PR-shaped with `--pr <pr>`, so a run that states its PR can only end through the `--require-ci <pr>` gate for that same PR. A finish with no gate is refused, and a finish that sets `unresolvedCompare` is refused with it. `--pr <n>` with `--require-ci <m>` for another pull request is a usage error at parse time, because both flags arrive on one command line, so that run never starts. The gate flag is a run input, so no turn supplies it and the refusal ends the run. A base branch with no required check does not refuse the declaration when every required-check source stated that it holds none: the gate passes on the PR head, the clean reviewed tree, and the merge state, and records it (issue #302, issue #336).
  - Runs an optional `--test-cmd <command>` before each reviewer turn, in the runtime and outside the reviewer sandbox, so a read-only reviewer holds test evidence it cannot produce: the exit code and an output tail go to the reviewer prompt as advisory, untrusted evidence. See [ADR 0017](adr/0017-run-a-test-command-before-each-reviewer-turn.md).
  - Runs a Codex reviewer turn in the `workspace-write` sandbox when the operator passes `--reviewer-workspace-write`. The shell commands that the sandbox runs have network off, so the reviewer can run a targeted test or a probe. A user Codex execpolicy rule that allows `bash -c`, `sh -c`, or `zsh -c` is an exception, as ADR 0019 states. The orchestrator stays read-only. The mutation check detects a change instead of the sandbox preventing it. See [ADR 0019](adr/0019-opt-in-workspace-write-sandbox-for-the-codex-reviewer.md).
  - Records validated orchestrator actions, a `refusal` event for each finish a `--require-accept` or `--require-ci` gate refused and for each `run_worker` action a `--mode review-only` run refused, an `unresolved-compare` event for each finish that reports an unresolved PR-head compare, a `no-required-checks` event for each finish the `--require-ci` gate passed on a base branch with no required check, child results, one `invocation` event per CLI call with usage when the adapter exposes it, timestamps, exit code, and error when `--transcript` is provided. Raw orchestrator responses are not recorded.

See [Architecture Decision Records](adr/README.md) for background and architectural decisions ([ADR 0001](adr/0001-hybrid-orchestrator-runtime.md), [ADR 0002](adr/0002-harness-neutral-orchestrator-instructions.md)).

## Supported agents

The controller supports these CLI names:

- Claude Code: `claude`
- Codex CLI: `codex`
- Antigravity CLI: `agy` (alias: `antigravity`)
- OpenCode: `opencode` (OpenCode v2, npm `@opencode/cli`)
- GitHub Copilot CLI: `copilot`

Each adapter manages its own persistent session across turns. Model and effort arguments pass through to the CLI on every turn.

### Closing block recovery

The parent reads the closing block of the turn. If a child answers a late event after its closing block, the last message holds no block. The Codex and Copilot adapters expose every assistant message of the turn, so each returns the last message that holds a closing block attempt, and falls back to the last message when none does (issue #449). An attempt is a report label name (`Conclusion`, `Why`, `Blockers`, `Checks`, `Notes`, `Deferred`) or `Verdict`, in any case, anywhere in the message, followed by optional emphasis marks or whitespace and a colon. The rule has no lead-in condition, so any list, numbered, lettered, quoted, or decorated form counts, whether or not the block parses. A late plain-prose message that mentions a label mid-sentence, for example `the conclusion: none`, also counts and fails closed through `raw`. A later malformed block therefore still wins and surfaces through `raw`, and an earlier accept never overrides it. The OpenCode adapter joins all text parts, and the parser reads from the last `Conclusion:` line, so it already selects the last block. The stream names the assistant message of each text part in `part.messageID`. The join starts a part from a different message on its own line, so a late plain-text message does not glue to the last line of the closing block (issue #458). Parts of one message join unchanged, because the stream splits one response at token boundaries. A valid `messageID` names one message across the whole stream, so parts of one message that another message interrupts still join as one message, ordered by the first part of each message. Every part without a valid, non-empty string `messageID` joins one unidentified message for the whole stream, even when identified parts come between them, and that message is ordered by its first part. It never joins an identified message and never redirects a later part, so a malformed id cannot lift a mid-line `Verdict:` to a verdict, and an identified message cannot pair its `Verdict:` with an unidentified `Checks` line or the reverse. The unidentified message cannot tell its own parts apart, so it fails closed (issue #509). If it governs, its join yields accept, and the label lines of its closing block (`Conclusion:` through `Verdict:`, read from the last `Conclusion:` line) come from more than one part, the turn fails with an error, however the lines or the labels are split. A `Verdict:` part therefore never pairs with an earlier unidentified `Checks` line. The error carries the text of every message, as for interleaving. A block that sits whole in one unidentified part still parses, even when earlier parts mention a label. The join groups parts into messages first and decides the break on the whole text of the later message, because a label can span parts. The last closing block governs, and it governs alone (issue #467). Each message holds its parts at stream positions. If the position spans of two messages that hold a closing block attempt overlap, for example one block split across parts that another block interrupts, the order of the blocks is ambiguous and the turn fails with an error, so no accept can come from it. The first line of the error names the cause, and the lines after it hold the text of every message, joined in the same way, so the error envelope carries what the model wrote (issue #493). The interleaved stream error and the unidentified part error redact that text first (ADR 0017), then keep its last 4000 code units, cut on a code point boundary. A longer text is cut at the start, and a second line states the cut and the original length, so the envelope and the state file stay bounded (issues #510 and #529). The bound holds only for the text that the adapter produces. A later redaction pass with a different environment can grow the text past the bound. A pass with the same environment leaves the text unchanged. For example, the value `API_TOKEN` in `OTHER_SECRET` rewrites `[redacted:API_TOKEN]` (20 characters) to `[redacted:[redacted:OTHER_SECRET]]` (34 characters). This example is not the full condition. Otherwise the last such message governs and the join drops every earlier one, so a late message never combines with the fields of the earlier block. A late bare `Verdict: accept` after a full block gives an unparseable report with verdict `unknown` and no `Checks` line, so the `--require-accept` gate refuses. A message with no attempt stays, so narration before the block and plain prose after it remain in the response. The selection matches Codex and Copilot, except that those adapters return the governing message alone and never fail on interleaving. The following adapters cannot recover the earlier block:

- Claude Code: the adapter runs `--output-format json --verbose` and receives an array of events. It reads the session id and the main-loop model from those events, and it returns only the `result` text of the result event, the final assistant message, to the run.
- Antigravity CLI: the result object carries the final message in `response`, and the adapter reads no per-message field.

A late answer after a closing block on these two adapters replaces the report of the turn. The worker prompt rule against a background watcher and for a closing block of the whole turn (issue #433) is the only guard.

### Session resume after a failed turn

A failed first turn keeps its session. When the CLI reported a session id, the adapter stores it on the role state on every failure path, including a non-zero exit, a timeout, and a response-validation failure such as a missing response text, so the next turn resumes that session and the edits the failed turn left. Each adapter selects the reported id by its own rule, then requires the selected id to be a non-empty string. Claude and opencode take the first truthy id in the output, so an empty id is skipped and a later valid id is used, while a truthy invalid id, such as a number or an object, fails the turn. Codex takes the `thread_id` of its first `thread.started` event, and an empty or invalid one fails. Copilot takes the id of its last result event (`sessionId`, or `session_id` when `sessionId` is null or absent), and an empty or invalid one fails. When a failed Copilot first turn reports no id (absent or null, not an invalid one), the adapter keeps the pre-assigned id with `sessionUnconfirmed` if the session holds a saved turn (see the Copilot row below, ADR 0030). agy reads the `conversation_id` of its one result object, and an empty or invalid one fails. A failed selection stores nothing on a first turn and leaves a resumed turn with its stored id. In every adapter except agy, a resumed turn whose selected id differs from the stored id raises `resumeMismatchError`. agy has no mismatch check: a successful resumed turn stores the valid `conversation_id` its result carries, and it logs a warning only when stderr matches `conversation "<name>" not found`. A failed turn never changes the id of a resumed session in any adapter. Every adapter except agy keeps the resumed id or raises `resumeMismatchError` on a different one. agy adopts the `conversation_id` that its successful result carries, even when it differs from the resumed id, and logs a warning only when it resumed an id and stderr matches `conversation "<name>" not found`. A resumed agy turn is sent without the role preamble, so a new conversation that agy started has not received it. The Claude adapter refuses a different id from a resumed turn, as Codex, Copilot, and opencode do. A Claude first turn passes a pre-assigned UUID with `--session-id` and keeps it when the turn fails, unless the failed output reported another id, which wins. A kill that leaves stdout empty therefore keeps the id. Claude Code 2.1.292 probe, with the same prompt shape each time: (1) a first turn killed with SIGTERM 30 s into a `sleep 90` tool call printed nothing, wrote its session file, and `--resume` of the pre-assigned id answered with the earlier command in its history and echoed the id; (2) a first turn killed 0.4 s in wrote no session file, and `--resume` of its id exited 1 with `No conversation found with session ID: <id>` and empty stdout, so the next turn reaches the missing-session fallback below and reruns once as a first turn with a new pre-assigned id. A successful first turn adopts the id the CLI reports and logs a warning when it differs from the pre-assigned one. A resumed turn passes no `--session-id`. On the interactive `role dispatch` path, the adapter reports the pre-assigned id before it starts the CLI and the dispatcher writes it to the state file at once, so a parent crash during a first turn leaves the id, and the first turn after `--resume-interrupted` resumes that session. If the CLI never saved the session, that resume reaches the missing-session fallback. A failed write stops the turn before the CLI starts. A first turn that the CLI rejects with `Error: Session ID <id> is already in use.` (exit 1, empty stdout, that one line byte for byte, optional LF or CRLF; Claude Code 2.1.292) never keeps the id: the id names another session, so the state file records null and the next turn starts with a fresh id. The rejected turn is not rerun and charges its step. The adapter withdraws the id through the same callback as soon as it sees that rejection, before it rethrows, so the state file holds no rejected id while the turn ends. Only a crash in the instant between the rejection and that write can still leave it. The state file also marks a pre-assigned id `sessionUnconfirmed` until the CLI output reports the session, because an unrelated session of another work tree can hold the same UUID and `resumeMismatchError` cannot catch it: that session reports the same id. Before the adapter resumes an unconfirmed id, in crash recovery, after `--continue-from`, or on the next turn, it requires a Claude Code session file `<id>.jsonl` under `$CLAUDE_CONFIG_DIR/projects` (default `~/.claude/projects`) whose first user record names the id and this work tree and carries the marker `[agent-loop session <id> role <role>]`. The adapter appends that line to the prompt of every first turn. The id is a fresh random value that only the state of this run records, and the role is part of the marker, so another session in the same work tree, a session of another role, and a session of another id never match. Only the marker match reads session content, from the first 256 KiB of the file, and nothing of it is logged. An id that is not a canonical lowercase UUID is refused before any path is built. A symlinked project directory or session file is not followed, and only a regular file counts. `--continue-from` restores the `sessionUnconfirmed` mark with the id from the transcript, and a transcript whose mark is not a boolean is refused. An id that fails the check raises the missing-session error before any CLI starts, so the runtime clears it and reruns the turn as a first turn with a new pre-assigned id, with the preamble and no second step. A session store elsewhere reads as not owned. The headless loop does the same when `--transcript` is set (issue #564), for a Claude orchestrator, worker, or reviewer: it rewrites the transcript before the CLI starts, with the id and `sessionUnconfirmed` on that role, so a parent crash during a first turn leaves a transcript that `--continue-from` resumes after the ownership check. A rejected id is withdrawn the same way. The written file keeps that id until the next transcript write, so a crash during the turn leaves it on disk. The id is held in an in-memory overlay that the end of the CLI call clears, and the role state is not changed. The next write, at the latest the write at exit, records what the adapter decided: an id that the output reported, else the pre-assigned id with its mark, else none. Three limits apply. A failed transcript write only warns, as at exit. A run with no `--transcript` keeps no record, so a crash there still loses the id. The mutation check of an orchestrator or reviewer turn covers the whole Git work tree (the repository root, not only `--cwd`) and has no exemption. A transcript inside that tree therefore cannot be written during those turns. For those two turns the loop writes a session record outside the tree, `<tmpdir>/agent-loops/session-records/<key>.json`. For a transcript inside the tree, the loop also writes the transcript once before the first turn. That write adds `runNonce`, a random UUID of the run. The record has exactly eight fields: `version` (always 1), `transcript` (the key), `cwd`, `runNonce`, `transcriptSha256`, `role`, `sessionId`, and `sessionUnconfirmed` (always `true`). `transcriptSha256` is the digest of the transcript file that the loop wrote last. The record holds no task text. `--continue-from` ignores a record unless five tests pass. The record is a small regular file of the current user. It has exactly those fields. The id and the nonce are UUID strings, and no other type passes. It names this transcript and work tree. Its `runNonce` equals the one in the transcript. Its digest equals the digest of the transcript now. Every later transcript write removes the record and makes an older one stale. A valid record gives the id and the unconfirmed mark to a Claude role that has no id. The ownership check then always runs before the id resumes (ADR 0027). The third limit is a lost record. A clean-up of the temporary directory removes it. If the temporary directory is inside the work tree, the loop saves nothing before an orchestrator or reviewer turn and logs a warning. A refused ownership check on a resumed orchestrator id ends the run and keeps the id with its mark, because the orchestrator has no first-turn rerun, so the next `--continue-from` checks the id again. The restore runs inside the mutation check, so a failed snapshot after the turn cannot lose the mark. Not verified: the behavior on a Windows file system (path case, junctions, and rename over an open file), and the transcript left by a real process kill. The tests simulate the kill by reading the file mid-turn. The worker turn is not under the check and writes. Separate processes that share one transcript path have no write coordination: each write is atomic, and the last one wins. The Copilot adapter keeps the id that the result event of a failed first turn reports. When the output reports no id, it keeps the pre-assigned id with `sessionUnconfirmed` only if the session holds a saved turn (a `user.message` event in `events.jsonl`, see the Copilot row below and ADR 0030), because a failed turn that saved no turn leaves a session that holds nothing, and a kept id would skip the preamble for nothing. An id that the output reports but that is empty or not a string stores nothing. On Copilot CLI 1.0.90-4, a first turn that failed on a bad model printed no result event, and a later call with the same pre-assigned id completed and echoed that id. Issue #642 showed on Copilot CLI 1.0.96-2 only that a bad-model failure saves no turn. The 1.0.90-4 run did not check the session files, so that it behaved the same there is an inference. On 1.0.95, a call with the id of a successful first turn resumed that session.

When a resume fails because the CLI has no such session, the Claude and Codex adapters mark the error, and only for exit 1 without a timeout, cancel, or signal, with empty stdout and stderr that is the one verified line for the requested id, byte for byte, followed by at most one line ending (LF or CRLF). That line ending is the only normalization: leading or trailing spaces, blank lines, a second line, or any other text leave the error unmarked, so a real failure is never rerun. The runtime then clears the id and reruns the turn once as a first turn: a worker gets the role preamble again. The rerun charges no second step. The failed resume ran no model turn, so the step pays for the one requested turn, and the rerun happens at most once per turn. The transcript shows two `invocation` events with the same `stepsUsed`, and the state file keeps one `turns` entry (issue #360, ADR 0016).
