# Session resume

## Session resume after a failed turn

A failed first turn keeps its session. When the CLI reported a session id, the adapter stores it on the role state on every failure path, including a non-zero exit, a timeout, and a response-validation failure such as a missing response text, so the next turn resumes that session and the edits the failed turn left. Each adapter selects the reported id by its own rule, then requires the selected id to be a non-empty string. Claude and opencode take the first truthy id in the output, so an empty id is skipped and a later valid id is used, while a truthy invalid id, such as a number or an object, fails the turn.

Codex takes the `thread_id` of its first `thread.started` event, and an empty or invalid one fails. Copilot takes the id of its last result event (`sessionId`, or `session_id` when `sessionId` is null or absent), and an empty or invalid one fails. When a failed Copilot first turn reports no id (absent or null, not an invalid one), the adapter keeps the pre-assigned id with `sessionUnconfirmed` if the session holds a saved turn (see the Copilot row below, ADR 0030).

agy reads the `conversation_id` of its one result object, and an empty or invalid one fails. A failed selection stores nothing on a first turn and leaves a resumed turn with its stored id. In every adapter except agy, a resumed turn whose selected id differs from the stored id raises `resumeMismatchError`. agy has no mismatch check: a successful resumed turn stores the valid `conversation_id` its result carries. When that id differs from the requested one, agy started a new conversation: the adapter logs a warning and sets `conversationReplaced`, and it ignores stderr.

A failed turn never changes the id of a resumed session in any adapter. A resumed agy turn is sent without the role preamble, so a new conversation that agy started has not received it. A Claude first turn passes a pre-assigned UUID with `--session-id` and keeps it when the turn fails, unless the failed output reported another id, which wins. A kill that leaves stdout empty therefore keeps the id. Claude Code 2.1.292 probe, with the same prompt shape each time: (1) a first turn killed with SIGTERM 30 s into a `sleep 90` tool call printed nothing, wrote its session file, and `--resume` of the pre-assigned id answered with the earlier command in its history and echoed the id; (2) a first turn killed 0.4 s in wrote no session file, and `--resume` of its id exited 1 with `No conversation found with session ID: <id>` and empty stdout, so the next turn reaches the missing-session fallback below and reruns once as a first turn with a new pre-assigned id.

A successful first turn adopts the id the CLI reports and logs a warning when it differs from the pre-assigned one. A resumed turn passes no `--session-id`. On the interactive `role dispatch` path, the adapter reports the pre-assigned id before it starts the CLI and the dispatcher writes it to the state file at once, so a parent crash during a first turn leaves the id, and the first turn after `--resume-interrupted` resumes that session. If the CLI never saved the session, that resume reaches the missing-session fallback.

A failed write stops the turn before the CLI starts. A first turn that the CLI rejects with `Error: Session ID <id> is already in use.` (exit 1, empty stdout, that one line byte for byte, optional LF or CRLF; Claude Code 2.1.292) never keeps the id: the id names another session, so the state file records null and the next turn starts with a fresh id. The rejected turn is not rerun and charges its step.

The adapter withdraws the id through the same callback as soon as it sees that rejection, before it rethrows, so the state file holds no rejected id while the turn ends. Only a crash in the instant between the rejection and that write can still leave it. The state file also marks a pre-assigned id `sessionUnconfirmed` until the CLI output reports the session, because an unrelated session of another work tree can hold the same UUID and `resumeMismatchError` cannot catch it: that session reports the same id. Before the adapter resumes an unconfirmed id, in crash recovery, after `--continue-from`, or on the next turn, it requires a Claude Code session file `<id>.jsonl` under `$CLAUDE_CONFIG_DIR/projects` (default `~/.claude/projects`) whose first user record names the id and this work tree and carries the marker `[agent-loop session <id> role <role>]`. The adapter appends that line to the prompt of every first turn.

The id is a fresh random value that only the state of this run records, and the role is part of the marker, so another session in the same work tree, a session of another role, and a session of another id never match. Only the marker match reads session content, from the first 256 KiB of the file, and nothing of it is logged. An id that is not a canonical lowercase UUID is refused before any path is built. A symlinked project directory or session file is not followed, and only a regular file counts.

`--continue-from` restores the `sessionUnconfirmed` mark with the id from the transcript, and a transcript whose mark is not a boolean is refused. An id that fails the check raises the missing-session error before any CLI starts, so the runtime clears it and reruns the turn as a first turn with a new pre-assigned id, with the preamble and no second step. A session store elsewhere reads as not owned.

The headless loop does the same when `--transcript` is set (issue #564), for a Claude orchestrator, worker, or reviewer: it rewrites the transcript before the CLI starts, with the id and `sessionUnconfirmed` on that role, so a parent crash during a first turn leaves a transcript that `--continue-from` resumes after the ownership check. A rejected id is withdrawn the same way. The written file keeps that id until the next transcript write, so a crash during the turn leaves it on disk. The id is held in an in-memory overlay that the end of the CLI call clears, and the role state is not changed.

The next write, at the latest the write at exit, records what the adapter decided: an id that the output reported, else the pre-assigned id with its mark, else none. Three limits apply. A failed transcript write only warns, as at exit. A run with no `--transcript` keeps no record, so a crash there still loses the id.

The mutation check of an orchestrator or reviewer turn covers the whole Git work tree (the repository root, not only `--cwd`) and has no exemption. A transcript inside that tree therefore cannot be written during those turns. For those two turns the loop writes a session record outside the tree, `<tmpdir>/agent-loops/session-records/<key>.json`. For a transcript inside the tree, the loop also writes the transcript once before the first turn. That write adds `runNonce`, a random UUID of the run.

The record has exactly eight fields: `version` (always 1), `transcript` (the key), `cwd`, `runNonce`, `transcriptSha256`, `role`, `sessionId`, and `sessionUnconfirmed` (always `true`). `transcriptSha256` is the digest of the transcript file that the loop wrote last. The record holds no task text. `--continue-from` ignores a record unless five tests pass. The record is a small regular file of the current user.

It has exactly those fields. The id and the nonce are UUID strings, and no other type passes. It names this transcript and work tree. Its `runNonce` equals the one in the transcript. Its digest equals the digest of the transcript now.

Every later transcript write removes the record and makes an older one stale. A valid record gives the id and the unconfirmed mark to a Claude role that has no id. The ownership check then always runs before the id resumes (ADR 0027).

The third limit is a lost record. A clean-up of the temporary directory removes it. If the temporary directory is inside the work tree, the loop saves nothing before an orchestrator or reviewer turn and logs a warning. A refused ownership check on a resumed orchestrator id ends the run and keeps the id with its mark, because the orchestrator has no first-turn rerun, so the next `--continue-from` checks the id again. The restore runs inside the mutation check, so a failed snapshot after the turn cannot lose the mark.

Not verified: the behavior on a Windows file system (path case, junctions, and rename over an open file), and the transcript left by a real process kill. The tests simulate the kill by reading the file mid-turn. The worker turn is not under the check and writes. Separate processes that share one transcript path have no write coordination: each write is atomic, and the last one wins.

The Copilot adapter keeps the id that the result event of a failed first turn reports. When the output reports no id, it keeps the pre-assigned id with `sessionUnconfirmed` only if the session holds a saved turn (a `user.message` event in `events.jsonl`, see the Copilot row below and ADR 0030), because a failed turn that saved no turn leaves a session that holds nothing, and a kept id would skip the preamble for nothing. An id that the output reports but that is empty or not a string stores nothing. On Copilot CLI 1.0.90-4, a first turn that failed on a bad model printed no result event, and a later call with the same pre-assigned id completed and echoed that id.

Issue #642 showed on Copilot CLI 1.0.96-2 only that a bad-model failure saves no turn. The 1.0.90-4 run did not check the session files, so that it behaved the same there is an inference. On 1.0.95, a call with the id of a successful first turn resumed that session.

When a resume fails because the CLI has no such session, the Claude and Codex adapters mark the error, and only for exit 1 without a timeout, cancel, or signal, with empty stdout and stderr that is the one verified line for the requested id, byte for byte, followed by at most one line ending (LF or CRLF). That line ending is the only normalization: leading or trailing spaces, blank lines, a second line, or any other text leave the error unmarked, so a real failure is never rerun. The runtime then clears the id and reruns the turn once as a first turn: a worker gets the role preamble again. The rerun charges no second step. The failed resume ran no model turn, so the step pays for the one requested turn, and the rerun happens at most once per turn. The transcript shows two `invocation` events with the same `stepsUsed`, and the state file keeps one `turns` entry (issue #360, ADR 0016).

### `claude`: resume after a kill

A Claude resume of an unconfirmed id needs a session file that this work tree and role own. A kill before the client writes that file leaves no session. The turn then reruns as a first turn, or an orchestrator run ends and keeps the id with its mark. The commands, timings, and output are in [ADR 0016](https://github.com/andromarces/agent-loops/blob/main/adr/0016-resume-a-failed-first-turn-with-a-fallback.md), and Linux and the Windows symlink cases are not verified.

### `agy`: resume of a missing session

The adapter stores the valid id the result carries. When that id differs from the resumed one, with or without the stderr text, the adapter logs a warning. It also marks the state `conversationReplaced`. A resumed turn carries no preamble.

For a worker, the runtime then runs one preamble-only turn in the new conversation, in the same step. It never reruns the task, so its edits are not repeated. Limits: the task prompt reaches the new conversation before the preamble. The preamble-only turn can still write, because a worker turn has no mutation check.

A failed preamble turn only warns. The preamble-only turn carries the `Init task:` block with the preamble. A reviewer gets a task-only turn instead, in the same step: it carries the `Init task:` block and asks for no review and no verdict, and its reply is dropped. It costs one extra child turn and runs under its own mutation check, apart from the review turn. A failed task-only turn, other than by a cancel, records no delivery and makes the whole reviewer turn an error result with no verdict.

The next reviewer turn then carries the block, because `taskSentTo` names the old conversation. A task-only turn that runs in a third conversation delivers the task there and records that conversation, so the next turn does not repeat it. The turn is an error result too, because the conversation that gave the verdict never had the task. A verdict from a conversation without the task never counts toward a finish.

An orchestrator turn is read-only. The runtime reruns it once with the initial instructions before the same prompt. The earlier orchestrator turns are lost. Each of the two calls has its own mutation check, so an edit that the rerun restores is still detected.

A cancel after the replacement ends the turn as canceled. This includes a cancel in the preamble-only turn or the rerun. The turn keeps the id the CLI reported (ADR 0027) and leaves `conversationReplaced` set on the role. The next worker turn then sends the preamble with its task.

The role state also keeps `taskSentTo`, the id of the conversation that last carried the init task. The next worker turn sends the preamble without the `Init task:` block when `taskSentTo` names the session it resumes. The replaced conversation then sees the task at most once. A canceled turn that carried the task counts as delivered.

If the CLI dropped that prompt, the conversation never sees the task. A cancel in the reviewer task-only turn counts as delivered, like any canceled turn that carried the task, so the next reviewer turn does not repeat the block. The cancel leaves the mark set and gives no verdict, so a run that ends first has no accepted verdict from that conversation. The mark is stored in the run state of `role dispatch` and in the `--transcript` roles, and `--continue-from` restores it with the id.

A missing conversation returns a new `conversation_id`. A worker replacement then gets a preamble-only turn, a reviewer gets a task-only turn, and an orchestrator reruns with the initial instructions. The probe commands, the stderr warning, and the results are in issue #579, and issue #657 repeats them on Windows 11. Linux is not verified.

### `agy`: resume after a kill

The first turn used `agy --input-format text --output-format json --dangerously-skip-permissions`. The prompt asked to remember a word and to run `sleep 63; echo hi`. `SIGKILL` went to the `agy` process 15 s after the start. The conversation transcript shows `run_command` with status `RUNNING` as a background task. Stdout was empty, so the output named no id.

The conversation existed on disk as `~/.gemini/antigravity-cli/conversations/<id>.db`. A second call with `--conversation <id>` exited 0 and returned the same `conversation_id`. It answered `The secret word is PAPAYA, and the sleep command did not finish because the background task stopped during a server restart.`. A kill during a tool call therefore leaves a conversation that resumes. The adapter keeps no id, so it cannot resume it.

With `--output-format stream-json`, the first event (`init`) carries `conversation_id`. The adapter does not use that format. The tool shell stayed alive after the `agy` process ended, with parent pid 1. The kill probe is not verified on Linux or Windows, because no host of either kind was available in issue #675. No result contradicts the adapter. ADR 0016 holds the commands.

### `copilot`: resume of a missing session

A call with an existing `--session-id` resumes that session, and an id with no session creates a new one. The `result` event carries the session id that the adapter reads. The probe commands and results are in issue #375 and [ADR 0016](https://github.com/andromarces/agent-loops/blob/main/adr/0016-resume-a-failed-first-turn-with-a-fallback.md).

### `copilot`: session id of a failed first turn

When the output reports no id (the field is absent or null), it keeps the pre-assigned id, marked `sessionUnconfirmed`, only if the child process started and `<COPILOT_HOME or ~/.copilot>/session-state/<id>/events.jsonl` is a regular file in a real directory, neither followed through a link, whose first 256 KiB holds a `user.message` event (issue #642, ADR 0030). An id that the output reports but that is empty or not a string is invalid, and it stores nothing, with or without a saved turn. A failure before the prompt was recorded, such as a bad model or an unsupported effort, leaves no `events.jsonl` and keeps no id, so the next worker turn carries the preamble. A resume of an unconfirmed id runs the same check first.

A session with no saved turn raises the missing-session error before any CLI starts, and the runtime reruns the turn as a first turn with the preamble. A result event or a failed result that reports the kept id clears the mark. Another reported id leaves the kept id and its mark, and the mismatch error follows. A resumed turn never changes its id.

### `copilot`: resume after a kill

Copilot CLI 1.0.95 ran the first probe and 1.0.96-2 ran the second, because the CLI updated itself between them. Each probe used `copilot --session-id <fresh uuid> -s --no-ask-user --output-format json --allow-all-tools`, with the prompt on stdin: remember a codeword, then run `ping -n 60 127.0.0.1 > nul & echo PROBE_TOOL_DONE`. The probe read the stdout events and ended the process tree with `taskkill /F /T` 1.5 s after the first `tool.execution_start` event.

In both probes the first call exited 1, printed a `tool.execution_start` event with no `tool.execution_complete` event, and printed no `result` event. The second call used the same `--session-id` with the prompt `What codeword did I ask you to remember, and which shell command did you run? Answer in one line.` It exited 0 and its `result` event echoed the pre-assigned id. In the 1.0.96-2 probe the reply was `Codeword: ZEBRA933905; Command: ping -n 60 127.0.0.1 > nul & echo PROBE_TOOL_DONE`, which matches the first prompt. In the 1.0.95 probe the reply named the same command and declined to repeat the word, which it called secret.

The session file of each probe in `~/.copilot/session-state/<id>/events.jsonl` held two `user.message` events and one `tool.execution_start` event. The resumed session therefore holds the turn that failed after a tool call, and a failure of this kind leaves a session under the pre-assigned id. The result holds for a kill.

Issue #642 probed on 1.0.96-2, same host: a bad `--model` and `--reasoning-effort xhigh` on a model that does not support it each exited with an error and no result event, and left a session directory with `workspace.yaml` and no `events.jsonl`. An adapter run of a first turn that the timeout ended after the prompt was recorded (9 s to 13 s) kept the pre-assigned id with the mark, and one that the timeout ended before the prompt was recorded (3 s to 7 s) and the bad-model run kept none. A completed turn wrote `events.jsonl` with `session.start`, `user.message`, `assistant.message`, and `session.shutdown`. A model error in the middle of a model call could not be produced, and its failure ends like a kill with no result event, so the same file check decides it (test only).

Issue #398 repeated the kill on macOS 27.2 with Copilot CLI 1.0.96-2. Each call used `copilot --session-id <fresh uuid> -s --no-ask-user --output-format json`. The tool case also used `--allow-all-tools`. The probe sent `SIGKILL` to the `copilot` process. Each resume used the same `--session-id` and asked for the word of the first prompt.

A kill 3 s after the first `tool.execution_start` event of `sleep 60` left no `result` event on stdout. The session directory held `events.jsonl` with a `user.message` and a `tool.execution_start` event. The resume exited 0 and echoed the id. It answered `MANGO; no, the sleep command did not finish.`.

A kill 2.5 s after the start printed only MCP status events. It left a session directory with no `events.jsonl`. The resume answered `MANGO`. A kill 0.3 s after the start left no session directory. The resume exited 0 and answered `NONE`, so it started a new session under the id.

The result matches issue #641 on macOS. It adds no new contradiction of the adapter. The `copilot` command runs a Node loader that starts the native binary. A kill of the loader pid left the native process and the tool shell with parent pid 1. ADR 0030 keeps the id when `events.jsonl` holds a `user.message` event (issue #642). ADR 0016 holds the commands.

Issue #675 killed the native process instead, on macOS 27.2 with Copilot CLI 1.0.96-2. `SIGKILL` went to the native `copilot` child of the loader pid, 3 s after the first `tool.execution_start` event. The loader exited with code 1, and stdout held no `result` event. The resume with the same `--session-id` exited 0 and recalled the word of the first prompt. The tool shell stayed alive with parent pid 1, which issue #679 probes. No result contradicts the adapter, and ADR 0016 holds the command and the decisive output.

### OpenCode

#### Current contract

The OpenCode adapter passes `--standalone` on every turn. The turn runs against a private server instead of the shared background service, so the run does not depend on a background `opencode` service. Provider variables set on the shared service with `opencode service set env` do not apply to a standalone turn; provide them in the process environment. See [Background service](https://opencode.ai/v2/docs/cli#background-service) in the OpenCode CLI docs.

The stream splits one response across several `text` parts, and each part carries the `messageID` of its message. `joinTextParts` (`src/agents/opencode-text.mjs`) joins them into one response:

- Parts of one message join with no separator, except that a part opening a report label (`Conclusion:`, `Why:`, `Blockers:`, `Checks:`, `Notes:`, `Deferred:`) starts its own line, because the parser matches each label plain at column 0 and a glued label makes the whole block unparseable, so `raw` carries the response instead (issue #316).
- The reviewer `Verdict:` label is not one of them. A part boundary inside a sentence, or before the `Verdict:` line, keeps the text as the model wrote it, so a model that writes `Verdict:` after prose without a line break of its own yields `verdict: unknown`.
- A new message starts its own line (issue #458). Parts without a valid `messageID` form one unidentified message.
- The last message that holds a closing block attempt governs alone. Earlier messages that hold an attempt drop, and messages without an attempt stay (issue #467).
- The turn fails when two messages that hold an attempt interleave in the stream, or when the governing message is the unidentified one, joins to an accept verdict, and gets its closing block label lines from more than one part (issue #509). The error text is redacted (ADR 0017) and bounded to its last 4000 code units (issues #510 and #529).

A non-zero OpenCode exit reports the exit code and the provider detail, and no stream text. The message has the form `opencode exited with code <n>: <error.type>: <message>`. A signal, a timeout, and a spawn failure are reported as themselves, because the output of a killed process names a provider error that is not why the turn died (issue #326).

#### OpenCode error evidence

The error envelope is verified on macOS and Windows (issues #339, #605, #638, #676, #699, and #677). Linux, a `Retry-After` above 30, and a 429 body that is not JSON are not verified. A rate-limited turn that ends before the dispatch timeout is not verified. The #638 retry past 110 seconds stays unresolved. The npm package `opencode-ai` was not run. The probe logs are in [ADR 0105](https://github.com/andromarces/agent-loops/blob/main/adr/0105-keep-probe-evidence-in-the-linked-issue-or-adr.md#opencode-provider-error-probes).

## Reviewer replacement and the task-only turn

The adapter that sets `conversationReplaced` is agy. A resumed turn whose `conversation_id` differs from the requested id logs a warning, sets the mark, and adopts the new id. The runtime then runs the task-only reviewer turn in that conversation before the dispatch returns.

Reviewer conversation replacement and an interrupt during the task-only turn are verified on agy 1.4.12 with model `gemini-3.8-flash-low` on macOS 27.2. Windows, Linux, and the other CLIs are not verified. The probe logs are in [ADR 0105](https://github.com/andromarces/agent-loops/blob/main/adr/0105-keep-probe-evidence-in-the-linked-issue-or-adr.md#reviewer-replacement-live-checks).
