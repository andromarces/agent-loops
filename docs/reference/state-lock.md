# State lock

Part of [Child dispatch](role.md). The lock guards the run state file of `agent-loop role`.

The lock is fail-closed on ambiguity: a contender that finds a lock it cannot read, or whose content a running writer has not written yet, exits non-zero and never removes it; only a lock whose owner reads as dead (its recorded pid is dead, or alive but with a valid start-time stamp that differs from the stamp now at that pid, see below; a valid `linux-proc` stamp of another PID namespace, or any valid `linux-proc` stamp while the reader cannot read its own PID namespace, keeps the owner alive even when its pid is dead here), or an unparseable lock that no writer can own, is treated as stale. A writer owns an unparseable lock while the temp file that it writes before it creates the lock (a marker named with its pid and a per-process token) has a live pid, at any age. A writer of an older version leaves no marker, so an unparseable file with no live marker is stale only once it is older than a 60 s grace window.

A lock whose owner reads as dead is removed under a claim file `state.lock.reap.<digest>`, a fixed-length name at every nesting depth, keyed by the SHA-256 of the guarded file name and its stale content, that only one contender can create. Each lock and claim records a random nonce with its pid, so the content of every acquisition is unique. The lock is deleted only if it still holds the content that was read as stale, so a lock that a new owner created in between survives, even with the same pid and start time, and the contender exits as busy. A lock written without a nonce by an older version is read the same way and is matched by content alone, so an older-version owner with the same pid and start time in the same millisecond would be taken for the stale lock. This protection holds only when every contender runs this version or later: an older-version contender removes a stale lock without a claim and keeps the original race with any other contender.

A contender that finds a live claim exits as busy, and a lock that cannot be re-read is kept. A claim left by a crashed process is removed the same way, under a claim keyed by its own content, and a chain of more than two crashed claims fails closed. Every successful lock acquisition also removes the orphaned claim files beside the lock (issue #452, ADR 0020), through the same claimed removal, so exactly one process acts on each claim. When: a claim whose owner reads as dead is removed at the next acquisition. An unparseable claim (created but not yet written, on the exclusive-create fallback) with no live marker is removed at the first acquisition after it is older than the 60 s grace window, so a fresh one stays until then. A claim whose owner does not read as dead (its pid is alive and its stamp matches, or the stamp rules below read it as alive), an unparseable claim with a live marker, and a claim that cannot be read are never removed while that holds.

The marker name carries a per-process token, so a process that reuses a pid writes its marker to a path of its own, and the prune removes only a marker with a token whose pid is dead. The `<pid>.<n>.tmp` marker of an older version is honored for liveness and never removed, so one that a crashed older version left stays on disk. A running writer of an older version leaves no marker and keeps its file only while it is younger than the grace window (known limit). Each lock and claim also records a start-time stamp of the owner, `<kind>:<value>`, with its pid (issue #498). The kind depends on the platform. On Linux it is `linux-proc:<PID namespace>:<boot id>:<ticks>`: the inode in the target of `/proc/self/ns/pid`, the boot id from `/proc/sys/kernel/random/boot_id`, and field 22 of `/proc/<pid>/stat` (clock ticks since boot). It is read with no spawn and does not depend on the wall clock, so a clock step never changes it.

The stamp is read only when the `NSpid` line of `/proc/self/status` has exactly one entry and that entry equals `process.pid`. proc_pid_status(5) (Linux 4.1 and later) defines the entries as the pid in each PID namespace that the process belongs to: the leftmost in the namespace of the process that mounted the procfs, then one for each nested inner namespace. One entry therefore means that the `/proc` mount is a view of the namespace of the caller, and two or more mean a mount of an ancestor namespace, where `/proc/<pid>/stat` can describe an unrelated process. The check proves only that the mounter namespace is the caller namespace. Otherwise (two or more entries, another pid, a missing `NSpid` line on a kernel older than 4.1, an unreadable status, or a line that does not parse) there is no stamp, on the writer and on the reader alike. On macOS it is `darwin-lstart:<epoch seconds>` from `ps -o lstart=` run under `TZ=UTC` and `LC_ALL=C`, with a 5 s timeout.

On Windows it is `win32-creation:<epoch seconds>` from the process creation time that `powershell.exe` returns, with a 5 s timeout. Any other platform records no stamp. The macOS and Windows kernels store the creation time once at process creation, so a clock step afterward should not change it. That comes from the platform documentation and source, and no test steps a clock, so it is unverified. A stamp is valid only in exactly these forms: the namespace and ticks are digits, the boot id is a UUID, and the epoch seconds are 1 to 15 digits (no sign, fraction, exponent, or non-finite value). A live pid reads as a reused pid, and its lock or claim is taken over, only when the recorded stamp and the stamp now at that pid are both valid, of the same kind, and differ. For `linux-proc` the pair must also have the same PID namespace, and any difference in boot id or ticks counts. For the other kinds the difference must exceed 2 seconds, which covers their one-second resolution and not a clock step.

For a live pid, every other case reads as alive: no recorded stamp (a lock of an older version, or the number of an earlier revision), an invalid recorded or fresh stamp, a kind mismatch, a `/proc` view that fails the `NSpid` check, and a current read that fails, times out, is empty, or does not parse (a `ps` line must name a date that exists, such as not the 31st of June). A reused pid then keeps that file until its process exits, and reuse never reads a running owner as dead (known limit). A valid `linux-proc` stamp is also checked before the pid is looked up: when its PID namespace differs from the reader namespace, or the reader namespace cannot be read, the owner reads as alive whatever its pid is here. A differing namespace means the pid belongs to another namespace (a container that shares the runs root), so it says nothing about the owner in this one. An unreadable reader namespace means the reader cannot tell whether the stamp namespace is its own, so it keeps the lock.

A lock without a valid stamp, or with a `darwin-lstart` or `win32-creation` stamp, skips this check: a dead pid reads as dead, and a live pid follows the stamp rules above. A lock with a valid `linux-proc` stamp that this check keeps is never taken over, even when its owner is dead: a crashed owner of another namespace keeps its lock, and so does a crashed owner of this namespace when the reader cannot read its own PID namespace. To free it, check that the owner is gone, then remove the lock file (and any `.reap.<digest>` claim beside it) by hand (known limit). A process reads its own stamp once, on its first lock creation. That costs no spawn on Linux, one `ps` on macOS, and one `powershell.exe` startup on Windows, bounded by the 5 s timeout. The Windows startup cost was measured on 2026-10-23 (issue #511, issue #709) on Windows 11 Pro 10.0.26220 with 16 CPUs, Windows PowerShell 5.1.26100.9739 (Desktop edition), and Node v26.8.1, while other runs loaded the host (CPU load 21% before and 63% after the samples, about 45 `node` processes running).

Over 15 fresh Node processes that each read their own stamp, the median was 804 ms and the range was 763 to 1207 ms. Every read returned a valid stamp. A bare Node start took a median of 64 ms on the same host. A cold start after a reboot and an idle host were not measured. Each process that takes a lock pays this cost once, and no cheaper source exists without a native dependency (known limit). A lock that cannot be read at all is kept and reported as busy. Lock creation is an atomic hard link, with an exclusive-create fallback on filesystems that have no hard links (FAT/exFAT, some network mounts); a lock or claim temp file with a token that a crashed process left is pruned on the next acquisition.
