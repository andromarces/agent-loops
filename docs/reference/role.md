# Child dispatch

## Interactive child dispatch: `agent-loop role`

An interactive parent session (Claude Code, Codex, or any harness with shell access) can dispatch one child turn without spawning a headless orchestrator:

```bash
# First call initializes the run state and dispatches the worker.
agent-loop role dispatch \
  --role worker \
  --cwd /path/to/work-tree \
  --task "Implement the change." \
  --mode work-first \
  --parent-session "$CLAUDE_SESSION_ID" \
  --worker claude --reviewer agy \
  --prompt-file ./prompt.txt

# Later calls read the configuration from the state file.
agent-loop role dispatch --role reviewer --cwd /path/to/work-tree --prompt-file ./review.txt
```

Operations: `dispatch` (default), `finish`, `abort`, `extend`, `declare-pr`, `wait-checks`.

- The run state lives at a fixed path derived from the resolved `--cwd` (`<os tmpdir>/agent-loops/runs/<sha256 of cwd, shortened>/state.json`, with `state.lock` beside it). There is no `--state` flag; `AGENT_LOOP_RUNS_ROOT` overrides the root for tests only.
- `--no-copy-local-files` is an init field: it turns off the copy of local files into a linked `--cwd` (see [Local files in a linked work tree](harness-entry-points.md#local-files-in-a-linked-work-tree)). A later call that passes it against a run that copied is refused, like every other init field. The init envelope carries `localFiles: {"copied": [...], "skipped": [...]}` when the copy ran, and no such key otherwise. A later dispatch adds `localFilesDiffer: [...]` when a copied file differs from its source in the main work tree, by name only and never overwriting the copy.
- `--copy-local-path <relative path>` is an init field that repeats once for each path. It adds an ignored path of the main work tree to the copy of local files for this run, for example a downloaded specification directory. The init refuses, before any state file is written or any child spawns, an absolute path, a path that leaves the main work tree or passes through a symlink or a junction, a path that holds a tracked file (also under another letter case), a path that holds a file that is not ignored, and use with `--no-copy-local-files`. The checks run when `--cwd` is the main work tree too. The copied files are named in `localFiles.copied`, and `localFilesDiffer` covers them. A later call that names another set is refused. See [Local files in a linked work tree](harness-entry-points.md#local-files-in-a-linked-work-tree).
- The init call requires `--parent-session`: the CLI refuses an init without it,
  and refuses an unexpanded placeholder such as `${CLAUDE_SESSION_ID}` or
  `%CODEX_THREAD_ID%`, before any state is written. A run through `role` is
  therefore always guarded; the headless `agent-loop` command is the explicit
  unguarded path.
- The init call registers one session entry per run at `<root>/session-runs/<parent-session>/<cwd hash>` (the state directory name) holding the state file path, so a parent guard hook (#57) can look a run up by session id even when `--cwd` is a different work tree. A later init call from the same session in the same work tree overwrites only its own entry, so simultaneous inits in different work trees each keep their entry and one parent session can drive several runs at once. The guard reads every entry for the session plus the legacy single-path `<root>/sessions/<parent-session>` file; init never writes the legacy file.
- Concurrent runs: `role dispatch` blocks until the child turn ends and prints one envelope. To run several loops from one parent session, interleave one dispatch turn per run and read each envelope before the next dispatch, or run each dispatch as a background shell command where the harness supports it and read each envelope when it completes. Pass each run's `--cwd` on every command; each run ends with its own `finish` or `abort`, and the guard stays engaged while any run is non-terminal.
- `--task-file <path|->` replaces `--task` on the init call and reads the task from a file. `-` reads it from stdin, which the prompt also uses by default, so pass `--prompt-file` with it. `--task` and `--task-file` cannot be combined, and an empty file is refused. `--task-file` keys init detection like `--task`, so do not repeat it on a later dispatch.
- Prompts come from stdin by default, or `--prompt-file`. `finish` reads the five-key summary as JSON on stdin; `abort` takes `--reason`.
- `extend --max-steps <count> --parent-session <id> [--cwd <dir>]` raises the step budget of a non-terminal run in place. `maxSteps` is an init field, so no other call changes it. A run that used its whole budget refuses every dispatch with `Step budget exhausted`, and a new run would start every role on a new session. `extend` keeps the same state file, so the stored role session ids and first-turn tracking keep working. The caller must pass the run's stored `--parent-session` id. A call with another id or none is refused and changes nothing, and the `extend` refusal does not name the stored id. Other subcommands do (see below). The id check does not identify the calling harness session, so a caller that read the id from the state file passes it, a child role included. A second boundary refuses a child caller of the run: the runtime sets `AGENT_LOOP_SPAWNED_RUN=<run keys>` in the environment of every worker and reviewer process, where the value is a comma-separated list of the keys of every enclosing run followed by the key of the dispatching run, a run key is the name of the run's state directory, the hash that every subcommand uses to find the run state, and `extend`, `finish`, and `abort` refuse a call whose list holds the key they use to find the run state, before they read the run state. A path that spells the work tree another way, such as a symlink alias, computes another key and finds no state. A child that names the work tree as the run does is refused even when the work tree is gone, and a parent `abort` over a missing work tree still works (issues #392 and #548, ADR 0014 point 8). The runtime sets no marker for the orchestrator or the parent session. A parent session that another run's child started, for example an interactive harness session inside a worker, inherits the marker of that other run, holds a different key for its own work tree, and still ends and extends its own run. Limits remain. A child that clears its environment, or a harness that filters it from shell commands, passes. A process keeps a marker it inherited, so an orchestrator or parent that a child of the same run started, in that run's work tree, is refused. A worker that a nested run starts holds the keys of the outer run and the nested run, so it is refused against both. The prompt rule in the orchestrator instructions is the remaining guard. `--parent-session` after init: `extend` requires it and refuses any other value than the stored id. `dispatch`, `finish`, and `abort` accept it as optional: when it is omitted they check nothing, when it is given they refuse a different value with `--parent-session cannot be changed after init (state holds: "<stored id>")`, which names the stored id, and when it equals the stored id they accept it. `dispatch` also refuses a malformed id when given. `wait-checks` reads no run state and ignores it. No call changes the stored parent session, so a run that another session resumed is unguarded for that session, and `extend` refuses that session's own id. It can extend only by passing the stored id, which `extend` compares as an id only, so the call succeeds for any parent-side caller that holds the id and gives no guard coverage. `dispatch`, `finish`, and `abort` run with no `--parent-session` at all. Abort and start a new run to get a guard (issue #435, ADR 0021). `<count>` follows the init `--max-steps` range and must be larger than both `stepsUsed` and the current `maxSteps`; any other value is refused and the state file stays unchanged. It works from `active`, `dispatched`, and `interrupted`, leaves the lifecycle as it is, and refuses a terminal run. It prints `{"status": "ok", "lifecycle": "active", "maxSteps": 40, "stepsUsed": 20}`. Every change is appended to `budgetChanges` in the state file as `{from, to, stepsUsed, at}`, so the history shows after which turn the budget changed (ADR 0014).
- `declare-pr --pr <pr> --parent-session <id> [--cwd <dir>]` sets `pr` once on a non-terminal run that declared none at init, for a task whose worker opens the pull request. The change is one way, from no PR to a number: a run that already has a PR, a terminal run, a `review-only` run, a missing or wrong `--parent-session`, and a child role of the run are refused. After it the run behaves as one that passed `--pr` at init: reviewer prompts carry the runtime-read required-check status, and `finish` must end through `--require-ci <pr>`. The envelope is `{"status": "ok", "lifecycle": "active", "pr": 42}`. The headless loop has no such call. See ADR 0041 and the orchestrator guide.
- `wait-checks --pr <pr> [--all [--expect <check name>]...] [--head <sha>] [--cwd <dir>] [--timeout <seconds>]` waits for the required checks of that pull request and prints `{"status": "ok", "pr": 42, "timedOut": false, "head": "<sha>", "checks": [{"name": "ci", "state": "SUCCESS", "bucket": "pass"}]}`. `head` names the commit that `checks` describe. `gh pr checks` queries by PR identity and names no commit, so the wait never takes a check state from it. Each poll reads the PR head `<sha>` and the base branch with `gh pr view <pr> --json headRefOid,baseRefName`, runs `gh pr checks` for its exit-code outcome, and reads every state from the check runs and commit statuses of `<sha>` by SHA (`repos/<slug>/commits/<sha>/check-runs` and `.../status`, every page). The required wait judges each required context as the `--require-ci` gate does, with the gate's own matching and verdict: the contexts come from `requiredContexts` (repository rulesets with `integration_id`, classic protection with `app_id`, and the names `gh pr checks --required` lists), an app-qualified context is satisfied only by a check run of that app, the latest matching entry decides, and a context with no entry on `<sha>` is pending. The `--all` wait judges the latest check run of each name and app and the latest commit status of each context. A head that moves away and back, or a stale view, therefore cannot put another commit's checks under `head`. The states of `<sha>` only make the outcome stricter: a failing state of `<sha>` settles the wait, and a pass needs both the `gh pr checks` outcome and every state of `<sha>` to pass, so exit 8 or the no-check-yet reply keeps the wait running while `<sha>` shows a pass, until the bound ends it with `timedOut: true`. A failure that `gh pr checks` lists settles the wait whatever `<sha>` shows, and it is reported in `prFailures`, apart from `checks`, because it is PR-level evidence that is not pinned to `<sha>`: `checks` holds only states read for `head`, and a parent never records a pass from an envelope that carries `prFailures`. `prFailures` appears only when `gh pr checks` listed a failure in the last poll, and it survives a bound that a later read reaches and a commit or source read that fails (`head: null`, empty `checks`). The required wait refuses a context it cannot resolve, with the rule of the supplied status (`requiredResolutionRefusal`): a ruleset or protection source that cannot be read, a source reply that cannot be parsed, and a failed read of the required names each exit 1 with `status: "error"` before any state is judged, because such a source can hold a required check or an app qualifier that the wait never saw; a listed failure still settles the wait then, and the `--all` wait reads no source. A commit read that fails, or that returns a reply the wait fails to parse or order, is an error too, with one exception. The commit reads use the endpoints of the gate's reads, and neither the wait nor the gate uses `gh --paginate`: each sends one `gh api --include` request per page, for the documented page number (`?per_page=100&page=N`), and never follows the `Link` header. A reply, a retryable 5xx included, whose `Link` header names a host other than the request host (`GH_HOST`, else the default host of `gh`, and its API host), or a target that is not a URL, ends the read with an error, is never retried, and is never requested. Each `gh` output then holds exactly one exchange, and `gh` writes the status line of that request first, followed by the headers, a blank line, and the body, so body bytes can only follow the status line and never form a status block of their own. The default host of `gh` is the one host of its configuration, or github.com for none or several. The read takes it from `gh auth status --json hosts`, run once per read for a reply that carries a `Link` target, with `GH_TOKEN` and `GITHUB_TOKEN` removed from that one call, because either variable adds github.com to the listing. A failed call and a reply of another shape name no host, so every target is then refused. Observed with `gh` 2.103.1 against a local server: a 403, a 502 with an empty, JSON, or HTML body, and a 403 whose body held a forged status block each wrote their own status line first, a redirect showed only the status line of its final reply, and `gh` itself rejected a 403 body that held extra bytes after one JSON value. The wait takes the status only from that first line and never reads the error text, which carries server-supplied text. A failed read is retried on the next poll, inside the bound, only when the first-line status is exactly 500, 502, 503, or 504 and the rest of stdout after the headers is empty or exactly one JSON value, and a pass on a later poll settles the wait. A successful page needs a 2xx first line and a remainder that is exactly one JSON value, checked on the whole remainder, so trailing bytes make the read an error. For an endpoint that reports `total_count`, such as the check runs, the read ends only when the collected count equals it: an empty or short page while the count is unmet, a `total_count` that changes or disappears between pages, and a collected count above it are each an error, never a pass, so a failure on a later page is never skipped. For an endpoint with no `total_count`, the first page of fewer than 100 items ends the read. The read stops with an error after 100 pages, and a successful read joins the pages into the array that the slurped read printed. Each page read stays inside the wait bound. Trade-off: a real 5xx whose body is HTML or plain text, as a proxy sends, stays terminal, because its body cannot be told apart from forged text. Relation to issue #1033: the gate reads and the ruleset read share this pager, so no read follows a reply-supplied `Link` URL. Any other failure also ends the wait at once: another first-line status, such as 501 or a 4xx, whatever its body says, a failure with no status line, and a body that fails to parse. A later poll that completes replaces the error of an earlier one, whether it settles, skips its reads because the PR head is another commit than `--head`, or reads the commit. A wait that reaches the bound while the latest completed poll failed with a retryable status exits 1 with `status: "error"` and that error, with no `timedOut: true` and no pass, unless `gh pr checks` listed a failure in that poll, which `prFailures` reports with the bound as before. The retry covers `wait-checks` only: the `--require-ci` finish gate keeps failing closed on every read failure (issue #1025). `childExitUnconfirmed` covers every `gh` child of the poll, including a source read that the first failure left running to the ceiling, and it rides on every envelope, settled, timed out, or error. The PR head is the one read at the start of the poll, so the PR can have moved on by the time the wait returns, and a required check that no read of the PR lists yet is absent, as before. `--head <sha>` takes a full lowercase commit SHA of 40 or 64 hex digits, refuses an abbreviation, and is refused on every other operation: while the PR head is another commit the wait reads no checks and continues, and a wait that reaches the bound first returns `timedOut: true`, `head: null`, and an empty `checks`, never a pass. `head` is `null` only when no read completed (issue #961). It reads status only, so it writes no run state and needs no init, and it returns inside its own bound: `--timeout` is in seconds, defaults to 300, and refuses 0. The runtime owns the bound because `gh pr checks --watch` takes no timeout and a shell `timeout` is absent on Windows and on macOS without GNU coreutils (issue #329). The bound covers the whole command, not only the reads: it starts at command entry and no step of the command adds time to it. Work-tree validation runs inside the bound, with `assertGitWorkTree` carrying the remaining time to `execa` as `timeout` with `cleanup` and `killDescendants`, so a slow or hung `git` is terminated and a validation that reaches the bound refuses, because a work tree the probe never confirmed is not one the command may read. Every read is limited to the time the command has left, and a read that reaches the limit is stopped and then given five seconds to exit, so the total bound is `--timeout` plus five seconds. The `gh` child is terminated on expiry the same way: `SIGTERM` then `SIGKILL` after one second on macOS, and `taskkill /T /F` over the process tree on Windows. `timedOut: true` means the bound was reached, whether with a pending check or during a read; it is a completed read, and the envelope carries the last check states that were read, so an empty `checks` with `timedOut: true` means no check state was ever read. `childExitUnconfirmed: true` appears only when the five-second ceiling expired with the `gh` child still unaccounted for: the command does not claim an exit it did not observe, and a parent that sees it settles the outstanding `gh` process before starting another wait. The `gh pr checks` exit codes decide the outcome as the reviewer read states them: exit 0 with no pending check listed is settled, exit 8 is pending, and exit 1 is settled only when the output lists a failing required check, or when `gh` prints exactly `no required checks reported on the '<branch>' branch` and no output. That answer, matched with the pattern of the required-check gate, and only when the ruleset and classic-protection sources each state the absence as the gate decides it and the names read succeeded (the wait is stricter than the gate there, which ignores a failed names read), exits 0 with `"noRequiredChecks": true`, an empty `checks`, and `"timedOut": false`: it is not a read error and never a pass, and the parent dispatches the reviewer, which reads the CI status itself (issue #894), after one `wait-checks --all` run. The same `--all` run follows the required wait's refusal that no required-check source can state the required checks (the Free-plan 403 of #301, a source that `settled nothing`, `could not be read`, or `did not state that it holds no required check`): it is never a required-check pass, and a reply that could not be parsed or a failed read of the required names stays an unresolved read with no `--all` run (issue #1018). Measured live on 2026-10-17 (Windows 11 Pro 10.0.26220, `gh` 2.102.0, Node v26.8.1) on a pull request of a private GitHub Free organization repository with no required check: the required wait exited 0 with `{"status":"ok","pr":265,"timedOut":false,"noRequiredChecks":true,"checks":[]}`, and the following `--all` wait exited 0 with `{"status":"ok","pr":265,"timedOut":false,"checks":[{"name":"checks","state":"SUCCESS","bucket":"pass"}]}`. `--all` runs `gh pr checks <pr> --json name,state,bucket` with no `--required` for the same exit-code rules, and judges the check runs and commit statuses of the commit `head` names, with the same bound. Because it has no required-check answer, an exit 1 with no failing check listed is unresolved, including `no required checks reported on the '<branch>' branch`, and `noRequiredChecks` never appears in its envelope (issue #896). The one exception is the exact `no checks reported on the '<branch>' branch` reply with no output: it is an empty list, so the `--all` wait continues as the required wait does, and at the bound it returns `timedOut: true` with an empty `checks`, never a pass. A repository with no CI workflow therefore waits the full `--timeout` (issue #950). The `--all` wait ends that wait at once with `noCheckSource: true`, `timedOut: false`, and an empty `checks` when its first read lists no check, no `--expect` name is set, the read of the PR head by SHA finds no check run and no commit status, and no source can report a check for the PR head: the PR changes no file under `.github/workflows/` (`pulls/<pr>/files`, every page, `previous_filename` included), no workflow file of the base branch (`contents/.github/workflows?ref=<base SHA>`, then each file) names `pull_request`, `pull_request_target`, `push`, `merge_group`, `workflow_run`, or `check_suite` in its text, and neither the base head nor the head of the latest merged PR of that commit has a check run or a commit status. The merged PR comes from `commits/<base SHA>/pulls` (the pager of the commit reads): the entry that is merged into the base branch with the latest `merged_at`, whose head SHA the probe reads like the base head. A PR on that commit that is not merged or targets another branch is no evidence, an entry of another shape keeps the wait, and no merged PR adds no read (#1062). The base branch resolves to one SHA first (`commits/<base>`), every base read uses it, and a base branch or PR head that moved by the end keeps the wait. A missing workflow directory (the exact `Not Found (HTTP 404)` reply) counts as no workflow. Each read is bounded by the wait. The PR files use the pager of the commit reads, and the single reads (`readOne`) share the validation of that pager (`readReply`): the `Link` host check of every reply (#1033), the first-line status, a 2xx status block, one JSON value, and the 5xx retry classification (#1025), and a success with a `Link` header is refused. A missing workflow directory is only the exact 404 reply: a 404 status line, exactly `gh: Not Found (HTTP 404)`, a JSON body, and no `Link` target. A workflow file needs `type: file`, well-formed base64 whose bytes equal `size` and are valid UTF-8, and no backslash or control character in its text, because a YAML escape can spell an event name. A read that fails, cannot be parsed, has another shape, or is at an API cap (3,000 PR files, 1,000 directory entries) keeps the normal wait. The envelope is never a pass: the parent dispatches the reviewer, records the CI status as not verified, and reads no workflow itself. The limit is that the probe reads two commits, the base head and one merged PR head, so a provider that skipped both, that registers later, or that reports on a base head with no merged PR (a direct push) stays unseen (issues #1054, #1062). `--all` is refused on every other operation. `--expect <check name>` (repeatable, needs `--all`, refused on every other operation) keeps the `--all` wait running until each named check has a check run on `<sha>`. A name matches the name of a check run exactly: it is trimmed, case-sensitive, and any app qualifies, and a commit status of that name never matches. An empty name is refused and a repeated name is accepted. Commit statuses still count in the overall pass evaluation: a check that a third-party app registers after the first ones passed is otherwise absent, so an early pass is not evidence. A name that never registers ends the wait at the bound with `timedOut: true` and the name in `awaiting`, never a pass, and a failing check still settles the wait (issue #978). Any other exit 1, and any output that is not a check list, exits 1 with `status: "error"` and no check state, so an unresolved read never reads as a pass. Every check item is read as a name plus a `state` or `bucket` the CLI knows; an item carrying no readable state is unresolved, so one item the CLI cannot read cannot settle the wait as a pass. A check that has not started is absent from `checks`, because the command omits it, so an empty list means no required check has reported and the wait continues. `--cwd` must be inside a Git work tree, as it is for `dispatch`.
- The state file records `task`, `mode`, `cwd`, `parentSession`, `maxSteps`, `timeout`, `stepsUsed`, `lifecycle`, `pr` (the declared run PR, or `null`), `roles.{worker,reviewer}.{kind,model,effort,sessionId}` (`roles.worker` is null in `review-only`), `lastDispatch`, and `lastResult`, plus `budgetChanges` after an `extend`, `summary` or `reason` when terminal, `unresolvedCompare` when a finished run recorded an unresolved PR-head compare, `noRequiredChecks` when a gated finish passed on a base branch with no required check, and `resumeDecision` when a maintainer resumed an interrupted run. Updates are atomic (temp file plus rename); exclusive access uses `state.lock` with a stale-lock check on the owner pid.
- Every run keeps a turn history without `--transcript`: `turns` holds one entry per charged step, in order, surviving every later overwrite of `lastDispatch` and `lastResult`. Each entry is `role`, `status`, `verdict`, `head`, and `at`; report and response text stay out. `status` is `ok`, `error`, or `interrupted`, where `interrupted` marks a charged turn whose outcome is unknown and therefore carries no verdict and no head. The call that recovers a run from `dispatched` into `interrupted` runs no child and charges no step; it records the turn the crash left unrecorded, using that turn's `lastDispatch` role and time. A dispatch refused past `maxSteps` bounds the array at `maxSteps` fixed-shape entries. The accepted `--max-steps` range is 1 to 9007199254740991 (`Number.MAX_SAFE_INTEGER`). The CLI refuses a flag outside it, and `dispatch`, `finish`, and `extend` re-check the stored `maxSteps` against the same range before reading the budget and name the field to correct, because a state file written by an earlier version or hand-edited carries the value past the flag check. Every budget a run reads is therefore a safe integer, and the step count always advances by exactly one per charged step. `abort` is exempt: it charges no step and reads no budget, so it still ends such a run, which is the only route to a terminal lifecycle when the stored value is out of range. A new init then starts normally and archives the old state file, so no field has to be hand-corrected.
- Lifecycle values: `active`, `dispatched`, `interrupted`, `halted`, `finished`, `aborted` (terminal: `halted`, `finished`, `aborted`). A turn interrupted between the CLI start and the state write leaves `dispatched` with a dead lock owner; the first call after the crash marks it `interrupted`, exits non-zero, and never repeats the turn, even with `--resume-interrupted`. From `interrupted`, only `abort` or an explicit `dispatch --resume-interrupted` is accepted. `--resume-interrupted` is refused with exit 1, before the step is charged, when another live process passes the session id of the dispatched Claude role through `--session-id`, `--resume`, or `-r` (as `--flag <id>` or `--flag=<id>`, ADR 0031 and ADR 0032). A `SIGKILL` of the dispatch leaves its `claude` child running, and the resumed turn would write the same session file. End that process or wait for it, and dispatch again. A process table that cannot be read logs a warning and lets the resume continue.
- The lock is fail-closed on ambiguity: a contender that finds a lock it cannot read, or whose content a running writer has not written yet, exits non-zero and never removes it; only a lock whose owner reads as dead (its recorded pid is dead, or alive but with a valid start-time stamp that differs from the stamp now at that pid, see below; a valid `linux-proc` stamp of another PID namespace, or any valid `linux-proc` stamp while the reader cannot read its own PID namespace, keeps the owner alive even when its pid is dead here), or an unparseable lock that no writer can own, is treated as stale. A writer owns an unparseable lock while the temp file that it writes before it creates the lock (a marker named with its pid and a per-process token) has a live pid, at any age. A writer of an older version leaves no marker, so an unparseable file with no live marker is stale only once it is older than a 60 s grace window. A lock whose owner reads as dead is removed under a claim file `state.lock.reap.<digest>`, a fixed-length name at every nesting depth, keyed by the SHA-256 of the guarded file name and its stale content, that only one contender can create. Each lock and claim records a random nonce with its pid, so the content of every acquisition is unique. The lock is deleted only if it still holds the content that was read as stale, so a lock that a new owner created in between survives, even with the same pid and start time, and the contender exits as busy. A lock written without a nonce by an older version is read the same way and is matched by content alone, so an older-version owner with the same pid and start time in the same millisecond would be taken for the stale lock. This protection holds only when every contender runs this version or later: an older-version contender removes a stale lock without a claim and keeps the original race with any other contender. A contender that finds a live claim exits as busy, and a lock that cannot be re-read is kept. A claim left by a crashed process is removed the same way, under a claim keyed by its own content, and a chain of more than two crashed claims fails closed. Every successful lock acquisition also removes the orphaned claim files beside the lock (issue #452, ADR 0020), through the same claimed removal, so exactly one process acts on each claim. When: a claim whose owner reads as dead is removed at the next acquisition. An unparseable claim (created but not yet written, on the exclusive-create fallback) with no live marker is removed at the first acquisition after it is older than the 60 s grace window, so a fresh one stays until then. A claim whose owner does not read as dead (its pid is alive and its stamp matches, or the stamp rules below read it as alive), an unparseable claim with a live marker, and a claim that cannot be read are never removed while that holds. The marker name carries a per-process token, so a process that reuses a pid writes its marker to a path of its own, and the prune removes only a marker with a token whose pid is dead. The `<pid>.<n>.tmp` marker of an older version is honored for liveness and never removed, so one that a crashed older version left stays on disk. A running writer of an older version leaves no marker and keeps its file only while it is younger than the grace window (known limit). Each lock and claim also records a start-time stamp of the owner, `<kind>:<value>`, with its pid (issue #498). The kind depends on the platform. On Linux it is `linux-proc:<PID namespace>:<boot id>:<ticks>`: the inode in the target of `/proc/self/ns/pid`, the boot id from `/proc/sys/kernel/random/boot_id`, and field 22 of `/proc/<pid>/stat` (clock ticks since boot). It is read with no spawn and does not depend on the wall clock, so a clock step never changes it. The stamp is read only when the `NSpid` line of `/proc/self/status` has exactly one entry and that entry equals `process.pid`. proc_pid_status(5) (Linux 4.1 and later) defines the entries as the pid in each PID namespace that the process belongs to: the leftmost in the namespace of the process that mounted the procfs, then one for each nested inner namespace. One entry therefore means that the `/proc` mount is a view of the namespace of the caller, and two or more mean a mount of an ancestor namespace, where `/proc/<pid>/stat` can describe an unrelated process. The check proves only that the mounter namespace is the caller namespace. Otherwise (two or more entries, another pid, a missing `NSpid` line on a kernel older than 4.1, an unreadable status, or a line that does not parse) there is no stamp, on the writer and on the reader alike. On macOS it is `darwin-lstart:<epoch seconds>` from `ps -o lstart=` run under `TZ=UTC` and `LC_ALL=C`, with a 5 s timeout. On Windows it is `win32-creation:<epoch seconds>` from the process creation time that `powershell.exe` returns, with a 5 s timeout. Any other platform records no stamp. The macOS and Windows kernels store the creation time once at process creation, so a clock step afterward should not change it. That comes from the platform documentation and source, and no test steps a clock, so it is unverified. A stamp is valid only in exactly these forms: the namespace and ticks are digits, the boot id is a UUID, and the epoch seconds are 1 to 15 digits (no sign, fraction, exponent, or non-finite value). A live pid reads as a reused pid, and its lock or claim is taken over, only when the recorded stamp and the stamp now at that pid are both valid, of the same kind, and differ. For `linux-proc` the pair must also have the same PID namespace, and any difference in boot id or ticks counts. For the other kinds the difference must exceed 2 seconds, which covers their one-second resolution and not a clock step. For a live pid, every other case reads as alive: no recorded stamp (a lock of an older version, or the number of an earlier revision), an invalid recorded or fresh stamp, a kind mismatch, a `/proc` view that fails the `NSpid` check, and a current read that fails, times out, is empty, or does not parse (a `ps` line must name a date that exists, such as not the 31st of June). A reused pid then keeps that file until its process exits, and reuse never reads a running owner as dead (known limit). A valid `linux-proc` stamp is also checked before the pid is looked up: when its PID namespace differs from the reader namespace, or the reader namespace cannot be read, the owner reads as alive whatever its pid is here. A differing namespace means the pid belongs to another namespace (a container that shares the runs root), so it says nothing about the owner in this one. An unreadable reader namespace means the reader cannot tell whether the stamp namespace is its own, so it keeps the lock. A lock without a valid stamp, or with a `darwin-lstart` or `win32-creation` stamp, skips this check: a dead pid reads as dead, and a live pid follows the stamp rules above. A lock with a valid `linux-proc` stamp that this check keeps is never taken over, even when its owner is dead: a crashed owner of another namespace keeps its lock, and so does a crashed owner of this namespace when the reader cannot read its own PID namespace. To free it, check that the owner is gone, then remove the lock file (and any `.reap.<digest>` claim beside it) by hand (known limit). A process reads its own stamp once, on its first lock creation. That costs no spawn on Linux, one `ps` on macOS, and one `powershell.exe` startup on Windows, bounded by the 5 s timeout. The Windows startup cost was measured on 2026-10-23 (issue #511, issue #709) on Windows 11 Pro 10.0.26220 with 16 CPUs, Windows PowerShell 5.1.26100.9739 (Desktop edition), and Node v26.8.1, while other runs loaded the host (CPU load 21% before and 63% after the samples, about 45 `node` processes running). Over 15 fresh Node processes that each read their own stamp, the median was 804 ms and the range was 763 to 1207 ms. Every read returned a valid stamp. A bare Node start took a median of 64 ms on the same host. A cold start after a reboot and an idle host were not measured. Each process that takes a lock pays this cost once, and no cheaper source exists without a native dependency (known limit). A lock that cannot be read at all is kept and reported as busy. Lock creation is an atomic hard link, with an exclusive-create fallback on filesystems that have no hard links (FAT/exFAT, some network mounts); a lock or claim temp file with a token that a crashed process left is pruned on the next acquisition.

- Two opt-in finish gates apply to `work-first` and `review-first`. `--require-accept` refuses a `finish` unless the latest turn is a reviewer `verdict: accept` with a `Checks` line and the current exact snapshot has the reviewed `head` and `digest`, so a change to an uncommitted state at the same commit is detected. `--require-ci <pr>` refuses unless the PR head equals the reviewed `head`, the reviewed tree is clean, the PR is not behind its base under a strict rule, has no merge conflicts, GitHub reports a known and unblocked merge state, and every required check passed on the commit GitHub evaluates; required contexts come from repository rulesets, classic branch protection, and `gh pr checks --required`. An empty set refuses when a configuration source settled nothing, and passes when every configuration source stated that it holds no required check; that pass carries `noRequiredChecks`, so a finish on such a branch stays distinct from one that verified a check (issue #336). The rule for that pass is one allowlist, and it fails closed. Each required-check configuration source is classified by what its reply proved. A ruleset read the gate cannot interpret has the class unknown, and it refuses the finish whatever the rest of the union holds, before the per-check pass, because that reply may carry a required-status rule the gate never saw; that is a failed or partial page, a read that the runtime cannot account for page by page (the pages are read by page number, a `Link` target on another host is an error, and every received page, empty pages included, reaches the classifier), an anomalous page sequence, which is no page at all, two or more empty pages, or an empty page beside a page that holds rules, and an unlisted or malformed rule type. A ruleset read of exactly one empty page is neither of those: its class is empty, a successful read that found no rule, so it contributes no contexts and the per-check pass runs on the other sources, so a classic-only repository whose required checks passed still finishes. Otherwise a finish passes on the absence only when no source named a required check and no source is unknown, so both sources must have stated the outcome, and an unknown classic-protection source keeps the empty-union refusal with the reason naming it. An exact list of every reply shape and its class is in [ADR 0012](https://github.com/andromarces/agent-loops/blob/main/adr/0012-establish-the-absence-of-a-required-check.md); the classes are absent, has-contexts, empty, and unknown, and the table states each one on both the normal and the relaxed path. Absent, the only class that lets a finish pass, has exactly one reply per source. For repository rulesets it is a read of every page that returns a non-empty array whose entries all carry a documented rule type and none is a `required_status_checks` rule; the read is paginated, so a rule on a later page is enforced rather than missed, and a body the gate cannot account for every page of is unknown. For classic branch protection it is exactly `gh: Branch not protected (HTTP 404)`, one trailing line break aside, which the endpoint writes only to a caller that can read protection. No successful classic-protection body proves an absence, because a classic-protected branch can require reviews without requiring a check, so a readable body that names no check is unknown. Has-contexts is a reply that named at least one required check. Empty is exactly one empty page: a successful read that found no rule, which contributes no contexts and is not a positive absence, so the empty-union refusal names it on the relaxed path. Unknown is every other reply, including a ruleset read of no page at all, a ruleset entry whose type is missing or is not a documented rule type, a malformed or unparseable body, an empty page inside a longer read, and every unreadable reply. A branch reaches the absence path where both sources state the outcome, so a ruleset-only branch does, while a branch with no ruleset at all does not, because its read is one empty page, and empty is not absent, and an empty page inside a longer read states nothing, and neither does a classic-protected branch that requires reviews but names no check. GitHub documents that the ruleset read returns active rules only, so a rule in a ruleset whose enforcement is `disabled` or `evaluate` never appears in it and never affects the classification. `gh pr checks --required` is never classified and never establishes the absence, because it lists only the checks that already reported and on a base branch with no required check it prints nothing, which is the same silence as a read failure. The gate takes required names from its stdout whatever the exit status, so a non-zero exit whose stdout holds that JSON still contributes names, and only a stdout that is not a JSON array of named checks contributes none. The observed replies for the two configuration sources are `Not Found` (404) for a token without repository admin, `Branch not protected` (404) for an admin on a branch with no classic protection, `Resource not accessible by integration` (403) for a `GITHUB_TOKEN`, and `Resource not accessible by personal access token` (403) for a fine-grained PAT without the Administration permission. A rate-limit or SSO 403 fails the run by design, because it matches no unreadable shape and is not read as a source at all. The exception to ruleset readability is a private repository on the GitHub Free plan, where the plan does not allow the rule at all. The Free-plan 403, `Upgrade to GitHub Pro or make this repository public to enable this feature.`, was measured on the classic protection, branch rules, and rulesets endpoints with an admin classic PAT and an admin fine-grained PAT, and a read-capable collaborator was not tested, so whether a non-admin sees the same 403 is unverified. **A private GitHub Free-plan repository still refuses a declared `--pr` run under this change, so this does not resolve #336 for it, and such a repository must omit `--pr`, which leaves the #286 gap in place.** Repository rulesets are readable with read access on a repository whose plan allows the rule, so a token without repository admin still gates through repository rulesets and through `gh pr checks --required` while the classic-protection source stays unknown. A blocked merge state refuses after the per-check pass, so a named check refusal keeps its name, and a required check that never started cannot escape the gate, through that refusal or, when no required check reported and a configuration source is unknown, the empty-union refusal; the gate cannot tell a missing check from an unmet review or another required rule, so a repository with required approvals also refuses until they are met, and a branch that states it has no required check still refuses while its merge state is blocked. A context qualified by an app (a ruleset `integration_id` or a classic-protection `app_id`) passes only on a check run from that app, and an unqualified copy of that name is dropped so it cannot judge the name by another app's run. GitHub computes the merge state lazily, so a retry shortly after a push can clear an `unknown` state. Each refusal names the failed condition. In `review-only`, a flagless `finish` keeps the current behavior and each gate fails with a clear error.

The parent reads only the closing block, so a pointer leaves the worker without the defect (issue #434). The block keeps its one-line, no-list format.
- The worker first-turn prompt has the same rule for every result the parent needs, such as findings, drafts, decisions, and open questions: each stands in full inside the closing block, and the worker never points at text outside it, for example "the decisions above" (issue #976).
- The reviewer is required to end with one explicit `Verdict:` line (`accept` or `reject`, parsed case-insensitively) inside its closing block. The verdict word alone, the word closed by a sentence period (`reject.`), or the word followed by a separator and a trailing clause (`reject — the state does not pass`) parses to that word, unless the clause names either verdict as a whole word. Any other malformed value, including a missing line or a line that names both verdicts, yields `verdict: unknown`; process success never implies acceptance.
- `--transcript <file>` appends one JSON line per `invocation` and `result` event, in the same shape as the headless mode, accumulating across calls. It stays a per-call flag; the `turns` array above is the history every run keeps without it.

Stdout carries exactly one JSON envelope, except for `role --help` and `role -h`, which print plain usage text and exit 0. All logs go to stderr.

A string error message prints unchanged. A message of `null` or `undefined` is not serialized. The error is then the text of the whole error value, for example `Error: null` for an `Error` and `[object Object]` for a plain object. Outside a handled child error, any other message value serializes once under the key `error`, exactly as the envelope serialized it before. Its JSON type and its `toJSON` redaction are kept, and a state file that records the result holds the same value. A message that serializes to `null`, such as `NaN`, `Infinity`, or a `toJSON` that returns `null`, then prints JSON `null`.

A value that cannot serialize, or that serializes to nothing (a function, a Symbol, or a `toJSON` that returns `undefined`), prints a fixed text instead. The fixed text is `[unserializable message]`, or the digits of a BigInt. The envelope therefore never fails to stringify, and an error envelope always carries `error`.

A handled child error result carries text, not a JSON value. A non-string value that the serialization yields prints as its JSON text, so `null` prints the string `"null"`. A string value, such as one that a `toJSON` returns, prints unchanged. A handled child error that timed out prints `<role> timed out after <seconds> seconds` instead of its message.

A message that throws when read prints `Unreadable error`, except for a handled child error that timed out. Before the child turn starts, a message that throws a canceled error prints `Interrupted by SIGINT` instead. Only a message that throws after the child turn starts ends with a recorded result in the state file.

If the stdout write itself fails, for example on a closed pipe, no envelope can be delivered. The command then writes `Failed to write the envelope to stdout: <code>` to stderr. It exits 1 when the command outcome was exit 0, otherwise it keeps that non-zero exit code:

```json
{
  "role": "reviewer",
  "status": "ok",
  "report": {
    "conclusion": "...",
    "why": "...",
    "blockers": "...",
    "checks": "...",
    "notes": "...",
    "deferred": "..."
  },
  "verdict": "accept",
  "reviewed": {
    "head": "...",
    "clean": true,
    "exact": true,
    "digest": "..."
  }
}
```

`report` is parsed from the closing block every child turn must end with. `conclusion`, `why`, and `blockers` are required; `checks` (the commands that ran and their results), `notes` (non-blocking findings), and `deferred` (out-of-scope items) are optional, and an omitted or empty label yields `null` for that field without making `report` null. Every child turn is asked for a `Checks` line, for a worker turn and a reviewer turn alike (issue #310), but only the reviewer `Checks` line is a gate input, so a worker `Checks` line is reported evidence and never an accept. Each label takes one line, plain at column 0. A `- ` list or an ordered `N. ` list (a `-` or a number and a period at column 0, exactly one space U+0020, then the item) that directly follows a report label line is that label's value, or joins the value that line already holds: the markers drop and the items join into one line with `; ` (issues #846, #879, and #915). A list under `Blockers: none` therefore reads `none; <item>`, never `none`. The reviewer `Verdict:` line is no report label, so a list after it stays unparseable. One nesting level folds too: a sub-item line (spaces up to the column where the parent item text starts, so two after `- ` and three after `1. `, then a hyphen, one space, then the item) after a `- ` or `N. ` item joins into that item with `, `, and several consecutive sub-items under one parent all fold into it (issues #870 and #915). One prose shape folds too: a blank line after the label line (or after its folded list), then one plain prose line, then a `- ` list directly under that line (dash items only: an ordered list there stays unparseable). The prose line must not start with whitespace (a nonbreaking or ideographic space counts), `*`, `_`, a backtick, `>`, or `#`, must not be a list, and must not hold a report label name or `Verdict`, in any case, followed by any run of `*`, `_`, or backtick marks (or none), whitespace (or none), and a colon, anywhere in the line. The prose and its list join the value of the label just above as `; <prose>: <items>`, the prose losing a trailing colon first (issue #898). A `- ` item or sub-item that opens with a bold report label name (`- **Notes:** ran`) inside such a run is item text and does not blank the block (issue #1006). Any other list in the closing block, for example bullets after the reviewer `Verdict:` line, a list outside any label, a list that a blank line or prose separates from its label outside that shape, a `*` line, a decorated or malformed label, or a `Verdict` line above a list, a bullet with no space after the marker or a separator other than one space (a tab, a nonbreaking space, two spaces) even under an empty label, a `*` or `+` bullet, an `N)` item, an ordered item that a blank line or prose separates from its label, a bold heading line that groups a `- ` list with no label directly above it, a `- ` item that opens with a bold report label name outside a list run under a label, an indented bullet that is not one nested level (no parent item, a second level, another indent width or marker), an indented label, or a decorated label makes the whole block unparseable, so `raw` carries the text instead of dropping it. This covers a label occurrence that a later repeat shadows, which also drops a list that the repeat shadows. A non-list line, for example a closing sentence, does not make the block unparseable. A `*` line is not always a list: a `*` line whose closing `*` a letter precedes, where the character right after the close is not a word character or `*`, and where nothing glued from that character on is a letter or an ASCII digit (`*file*`, `*glob src/a*`, `*use a* b`), reads as an emphasis run, so a spaceless `*` bullet of that shape is an accepted gap. The block still parses and every matching line drops with no `raw` signal, the same as any other line that is neither a label nor a list, because the bullet text and the emphasis text are the same bytes. Every other `*` line either is a list and blanks the block, for example `*item`, `* item`, or `*file*.mjs`, or is not a list and drops as prose, for example `**bold** note` (issue #275). When parsing fails, `report` is null and `raw` carries the whole response. `status: "error"` carries `error`, and every error path still prints one JSON object. The subcommand launches no orchestrator model and accepts no `--orchestrator` flags.

A reviewer envelope carries `reviewed`: `{ head, clean, exact, digest }` from the snapshot the runtime takes before the reviewer turn, so the child cannot misreport it. A reviewer turn in a run that named a PR, with `--pr <pr>` or with `--require-ci <pr>` on the headless command, also carries `prChecks`: `{ pr, head, status, checks, summary, advisory }`, the required-check status the runtime read for that PR head before the turn, where `status` is `pass`, `failing`, `pending`, or `unresolved`, `checks` names the checks in that state, `head` is the commit the status describes, `advisory` is always `true`, and `summary` is the one-line form the reviewer prompt carries. The state file keeps the same `prChecks` beside the response in `lastResult`, so a parent can compare the runtime read with the reviewer `Checks` line. The read resolves the PR head and reports a status only when it matches the local reviewed head. It reads the check runs and commit statuses of that commit by SHA, every page of each, so a head that moves away and back during the read cannot change what the status describes. A mismatch, a failed read, a reply or an entry that cannot be parsed or ordered, a classic protection reply that cannot be interpreted, a failed read of the required names, an unreadable ruleset source, a base branch with no required check, and a stalled read are all `unresolved` and never a failed turn. `advisory` is always `true` because the status is a report, and the `--require-ci` finish gate re-reads GitHub and enforces the condition. The status is a snapshot taken before the turn, so a check that starts or finishes later is not in it. A run that names no PR carries no `prChecks` (issues #320, #350). `head` is the commit, `clean` is true when the work tree has no uncommitted entries, `exact` is true when every entry has a content hash or is a deletion, and `digest` identifies the uncommitted state. A symlink hashes its link target text with a tag, so two links with different targets have different digests, dangling included, and a link never collides with a regular file that holds the same bytes.

The `finish` envelope is `{ "status": "ok", "lifecycle": "finished" }`, and the command exits 0. A finish that recorded an unresolved PR-head compare adds `"unresolvedCompare": true` and still exits 0, where the headless loop exits 4 for the same condition, and a verified finish keeps the envelope unchanged. A finish whose summary holds a key other than the five summary keys and `unresolvedCompare` is refused, names each unknown key, and leaves the lifecycle `active`; the headless `finish` action applies the same rule to its own keys and its summary (#1021).
