# Child dispatch

## Interactive child dispatch: `agent-loop role`

An interactive parent session (Claude Code, Codex, or any harness with shell access) can dispatch one child turn without spawning a headless orchestrator:

```bash
# First call initializes the run state and dispatches the worker.
agent-loop role dispatch \
  --role worker \
  --cwd /path/to/work-tree \
  --task "Implement the change." \
  --mode work-first \
  --parent-session "$CLAUDE_SESSION_ID" \
  --worker claude --reviewer agy \
  --prompt-file ./prompt.txt

# Later calls read the configuration from the state file.
agent-loop role dispatch --role reviewer --cwd /path/to/work-tree --prompt-file ./review.txt
```

Operations: `dispatch` (default), `finish`, `abort`, `extend`, `declare-pr`, `wait-checks`.

- The run state lives at a fixed path derived from the resolved `--cwd` (`<os tmpdir>/agent-loops/runs/<sha256 of cwd, shortened>/state.json`, with `state.lock` beside it). There is no `--state` flag; `AGENT_LOOP_RUNS_ROOT` overrides the root for tests only.
- `--no-copy-local-files` is an init field: it turns off the copy of local files into a linked `--cwd` (see [Local files in a linked work tree](harness-entry-points.md#local-files-in-a-linked-work-tree)). A later call that passes it against a run that copied is refused, like every other init field. The init envelope carries `localFiles: {"copied": [...], "skipped": [...]}` when the copy ran, and no such key otherwise. A later dispatch adds `localFilesDiffer: [...]` when a copied file differs from its source in the main work tree, by name only and never overwriting the copy.
- `--copy-local-path <relative path>` is an init field that repeats once for each path. It adds an ignored path of the main work tree to the copy of local files for this run, for example a downloaded specification directory. The init refuses, before any state file is written or any child spawns, an absolute path, a path that leaves the main work tree or passes through a symlink or a junction, a path that holds a tracked file (also under another letter case), a path that holds a file that is not ignored, and use with `--no-copy-local-files`. The checks run when `--cwd` is the main work tree too. The copied files are named in `localFiles.copied`, and `localFilesDiffer` covers them. A later call that names another set is refused. See [Local files in a linked work tree](harness-entry-points.md#local-files-in-a-linked-work-tree).
- The init call requires `--parent-session`: the CLI refuses an init without it,
  and refuses an unexpanded placeholder such as `${CLAUDE_SESSION_ID}` or
  `%CODEX_THREAD_ID%`, before any state is written. A run through `role` is
  therefore always guarded; the headless `agent-loop` command is the explicit
  unguarded path.
- The init call registers one session entry per run at `<root>/session-runs/<parent-session>/<cwd hash>` (the state directory name) holding the state file path, so a parent guard hook (#57) can look a run up by session id even when `--cwd` is a different work tree. A later init call from the same session in the same work tree overwrites only its own entry, so simultaneous inits in different work trees each keep their entry and one parent session can drive several runs at once. The guard reads every entry for the session plus the legacy single-path `<root>/sessions/<parent-session>` file; init never writes the legacy file.
- Concurrent runs: `role dispatch` blocks until the child turn ends and prints one envelope. To run several loops from one parent session, interleave one dispatch turn per run and read each envelope before the next dispatch, or run each dispatch as a background shell command where the harness supports it and read each envelope when it completes. Pass each run's `--cwd` on every command; each run ends with its own `finish` or `abort`, and the guard stays engaged while any run is non-terminal.
- `--task-file <path|->` replaces `--task` on the init call and reads the task from a file. `-` reads it from stdin, which the prompt also uses by default, so pass `--prompt-file` with it. `--task` and `--task-file` cannot be combined, and an empty file is refused. `--task-file` keys init detection like `--task`, so do not repeat it on a later dispatch.
- Prompts come from stdin by default, or `--prompt-file`. `finish` reads the five-key summary as JSON on stdin; `abort` takes `--reason`.
- `extend --max-steps <count> --parent-session <id> [--cwd <dir>]` raises the step budget of a non-terminal run in place. `maxSteps` is an init field, so no other call changes it. A run that used its whole budget refuses every dispatch with `Step budget exhausted`, and a new run would start every role on a new session. `extend` keeps the same state file, so the stored role session ids and first-turn tracking keep working. The caller must pass the run's stored `--parent-session` id. A call with another id or none is refused and changes nothing, and the `extend` refusal does not name the stored id. Other subcommands do (see below). The id check does not identify the calling harness session, so a caller that read the id from the state file passes it, a child role included. A second boundary refuses a child caller of the run: the runtime sets `AGENT_LOOP_SPAWNED_RUN=<run keys>` in the environment of every worker and reviewer process, where the value is a comma-separated list of the keys of every enclosing run followed by the key of the dispatching run, a run key is the name of the run's state directory, the hash that every subcommand uses to find the run state, and `extend`, `finish`, and `abort` refuse a call whose list holds the key they use to find the run state, before they read the run state. A path that spells the work tree another way, such as a symlink alias, computes another key and finds no state. A child that names the work tree as the run does is refused even when the work tree is gone, and a parent `abort` over a missing work tree still works (issues #392 and #548, ADR 0014 point 8). The runtime sets no marker for the orchestrator or the parent session. A parent session that another run's child started, for example an interactive harness session inside a worker, inherits the marker of that other run, holds a different key for its own work tree, and still ends and extends its own run. Limits remain. A child that clears its environment, or a harness that filters it from shell commands, passes. A process keeps a marker it inherited, so an orchestrator or parent that a child of the same run started, in that run's work tree, is refused. A worker that a nested run starts holds the keys of the outer run and the nested run, so it is refused against both. The prompt rule in the orchestrator instructions is the remaining guard. `--parent-session` after init: `extend` requires it and refuses any other value than the stored id. `dispatch`, `finish`, and `abort` accept it as optional: when it is omitted they check nothing, when it is given they refuse a different value with `--parent-session cannot be changed after init (state holds: "<stored id>")`, which names the stored id, and when it equals the stored id they accept it. `dispatch` also refuses a malformed id when given. `wait-checks` reads no run state and ignores it. No call changes the stored parent session, so a run that another session resumed is unguarded for that session, and `extend` refuses that session's own id. It can extend only by passing the stored id, which `extend` compares as an id only, so the call succeeds for any parent-side caller that holds the id and gives no guard coverage. `dispatch`, `finish`, and `abort` run with no `--parent-session` at all. Abort and start a new run to get a guard (issue #435, ADR 0021). `<count>` follows the init `--max-steps` range and must be larger than both `stepsUsed` and the current `maxSteps`; any other value is refused and the state file stays unchanged. It works from `active`, `dispatched`, and `interrupted`, leaves the lifecycle as it is, and refuses a terminal run. It prints `{"status": "ok", "lifecycle": "active", "maxSteps": 40, "stepsUsed": 20}`. Every change is appended to `budgetChanges` in the state file as `{from, to, stepsUsed, at}`, so the history shows after which turn the budget changed (ADR 0014).
- `declare-pr --pr <pr> --parent-session <id> [--cwd <dir>]` sets `pr` once on a non-terminal run that declared none at init, for a task whose worker opens the pull request. The change is one way, from no PR to a number: a run that already has a PR, a terminal run, a `review-only` run, a missing or wrong `--parent-session`, and a child role of the run are refused. After it the run behaves as one that passed `--pr` at init: reviewer prompts carry the runtime-read required-check status, and `finish` must end through `--require-ci <pr>`. The envelope is `{"status": "ok", "lifecycle": "active", "pr": 42}`. The headless loop has no such call. See ADR 0041 and the orchestrator guide.
- `wait-checks --pr <pr> [--all [--expect <check name>]...] [--head <sha>] [--cwd <dir>] [--timeout <seconds>]` waits for the required checks of that pull request and prints `{"status": "ok", "pr": 42, "timedOut": false, "head": "<sha>", "checks": [{"name": "ci", "state": "SUCCESS", "bucket": "pass"}]}`. `head` names the commit that `checks` describe, read by SHA, so a stale view never puts another commit's checks under it. The command reads status only, writes no run state, needs no init, and returns inside its own bound: `--timeout` is in seconds, defaults to 300, and refuses 0. A pass is never read from an unresolved read, a `timedOut: true` envelope, or an envelope that carries `prFailures`. `--all` waits for every check, `--expect` names checks that must register, and `--head` pins the commit. The full contract is in [wait-checks](wait-checks.md).
- The state file records `task`, `mode`, `cwd`, `parentSession`, `maxSteps`, `timeout`, `stepsUsed`, `lifecycle`, `pr` (the declared run PR, or `null`), `roles.{worker,reviewer}.{kind,model,effort,sessionId}` (`roles.worker` is null in `review-only`), `lastDispatch`, and `lastResult`, plus `budgetChanges` after an `extend`, `summary` or `reason` when terminal, `unresolvedCompare` when a finished run recorded an unresolved PR-head compare, `noRequiredChecks` when a gated finish passed on a base branch with no required check, and `resumeDecision` when a maintainer resumed an interrupted run. Updates are atomic (temp file plus rename); exclusive access uses `state.lock` with a stale-lock check on the owner pid.
- Every run keeps a turn history without `--transcript`: `turns` holds one entry per charged step, in order, surviving every later overwrite of `lastDispatch` and `lastResult`. Each entry is `role`, `status`, `verdict`, `head`, and `at`; report and response text stay out. `status` is `ok`, `error`, or `interrupted`, where `interrupted` marks a charged turn whose outcome is unknown and therefore carries no verdict and no head. The call that recovers a run from `dispatched` into `interrupted` runs no child and charges no step; it records the turn the crash left unrecorded, using that turn's `lastDispatch` role and time. A dispatch refused past `maxSteps` bounds the array at `maxSteps` fixed-shape entries. The accepted `--max-steps` range is 1 to 9007199254740991 (`Number.MAX_SAFE_INTEGER`). The CLI refuses a flag outside it, and `dispatch`, `finish`, and `extend` re-check the stored `maxSteps` against the same range before reading the budget and name the field to correct, because a state file written by an earlier version or hand-edited carries the value past the flag check. Every budget a run reads is therefore a safe integer, and the step count always advances by exactly one per charged step. `abort` is exempt: it charges no step and reads no budget, so it still ends such a run, which is the only route to a terminal lifecycle when the stored value is out of range. A new init then starts normally and archives the old state file, so no field has to be hand-corrected.
- Lifecycle values: `active`, `dispatched`, `interrupted`, `halted`, `finished`, `aborted` (terminal: `halted`, `finished`, `aborted`). A turn interrupted between the CLI start and the state write leaves `dispatched` with a dead lock owner; the first call after the crash marks it `interrupted`, exits non-zero, and never repeats the turn, even with `--resume-interrupted`. From `interrupted`, only `abort` or an explicit `dispatch --resume-interrupted` is accepted. `--resume-interrupted` is refused with exit 1, before the step is charged, when another live process passes the session id of the dispatched Claude role through `--session-id`, `--resume`, or `-r` (as `--flag <id>` or `--flag=<id>`, ADR 0031 and ADR 0032). A `SIGKILL` of the dispatch leaves its `claude` child running, and the resumed turn would write the same session file. End that process or wait for it, and dispatch again. A process table that cannot be read logs a warning and lets the resume continue.
- The lock is fail-closed on ambiguity: a contender that finds a lock it cannot read, or whose owner has not finished writing it, exits non-zero and never removes it. Only a lock whose owner reads as dead, or an unparseable lock that no writer can own, is stale, and one contender removes it under a claim file, only if the lock still holds the content that was read as stale. The owner is a pid plus a platform start-time stamp (issue #498), so a reused pid reads as a new owner. The stale rules, the stamp forms, and the measured Windows cost are in [State lock](state-lock.md).
- The reviewer turn runs under the same `withMutationCheck` as the headless loop: a detected mutation or snapshot error is fatal, keeps the charged step, and sets `halted`. No further dispatch is possible; the next run needs a new init call, which archives the halted file as `state.<timestamp>.json`.
- An init call is refused with exit 1, before it archives or writes any state, when another live process passes the id of a Claude role session through `--session-id`, `--resume`, or `-r` (as `--flag <id>` or `--flag=<id>`) and the current or an archived state file of the work tree records that id (ADR 0032). A hard kill of an earlier `role dispatch` leaves its `claude` child running. End that process or wait for it, and run again. A process table that cannot be read logs a warning and lets the init continue. The headless run has no such check for a fresh run.
- `mode: review-only` rejects `--role worker` as a hard guard and does not require `--worker` at init. `finish` is completion of the requested work, not code acceptance: it is accepted from `active` in any mode, and the caller records the reviewer verdict and unresolved findings in the five-key summary. The runtime checks that each of the five keys is a non-empty string and refuses a finish that holds any other key, naming each unknown key, and it does not check the content. The `role finish` stdin object allows the five summary keys and an optional boolean `unresolvedCompare`. The headless action object allows only `action`, `summary`, and an optional boolean `unresolvedCompare`, and its nested `summary` object allows only the five summary keys.
- `--mode <mode>` on the headless `agent-loop` command names the same three values the `agent-loop role` init call takes, so a caller learns the loop policy from one flag on both paths. The headless loop still chooses its own action order, and the flag is off by default, so a run without it behaves exactly as before, down to the byte-identical orchestrator prompt. A repeated `--mode` takes the last value, the way every other repeated value flag on this path already behaves. `--mode review-only` is the one mode that changes what a run accepts: it dispatches no worker, so it takes neither `--pr`, nor `--require-accept`, nor `--require-ci`, and each of those three is refused at parse time before any child turn runs, with the same wording the interactive path uses (`--pr` declares PR work, which needs the --require-ci gate; review-only rejects that gate. and --require-accept and --require-ci apply only to work-first and review-first; review-only accepts any verdict.). A `run_worker` action in that mode is refused at runtime and ends the run on exit 1 with the reason `mode review-only rejects a run_worker action`, the same hard guard the interactive path applies to `--role worker`: no worker turn runs, and no step is charged. `--mode work-first` and `--mode review-first` accept all three flags, and the headless orchestrator prompt states the mode the run was started with. The two paths reach the reviewer turn differently. `agent-loop role finish` in that mode applies no reviewer-turn rule of its own, because every reachable interactive run already has a reviewer turn: the init dispatch is itself that turn. A headless `--mode review-only` run owns its own action order and can reach a finish before any reviewer turn, so the runtime refuses that finish until a reviewer turn has run. That gate requires that a reviewer turn was dispatched, and nothing more: the turn can end in an error, so the finish can carry no reviewer report, no accept, and no readable verdict. The prompt instructs the orchestrator to record the reviewer status and verdict in `verified`; the runtime checks that each summary key is a non-empty string, refuses a finish that holds a key outside the allowed keys that the `mode: review-only` bullet above lists, naming each unknown key, and does not verify the content. `--require-accept` is refused in this mode on both paths, at `finish` on the interactive path and before the run starts on the headless path, so the headless run applies that reviewer turn with no flag of its own. A transcript records `mode` only when the run named one, so a mode-free run writes the same file shape as before (issue #337). One exception applies. A transcript inside the Git work tree also holds a top-level `runNonce`, a random UUID of the run. It binds the session record of [ADR 0027](https://github.com/andromarces/agent-loops/blob/main/adr/0027-save-the-session-id-of-an-in-tree-transcript-outside-the-work-tree.md) to that run. No transcript field before the first turn is unique to a run, so the record needs this field.
- `--pr <pr>` on the init call declares that the run's work is delivered on that pull request, so the run can only end through the `--require-ci <pr>` gate for the same PR. A base branch that states it has no required check does not refuse the declaration when every required-check source stated that it holds none: the gate passes on the PR head, the clean reviewed tree, and the merge state, and records it. A private GitHub Free-plan repository still refuses a declared run, so it must omit `--pr`. A `finish` with no gate, or with a gate for another PR, is refused without reading GitHub, because the interactive `--require-ci` arrives only at `finish`, and a `finish` that sets `unresolvedCompare` is refused because the gate resolves that compare. On the headless path both flags are on one command line, so `agent-loop --pr 42 --require-ci 7` is a usage error before the run starts. On the headless path, one refusal names every condition the finish broke, so read all of it rather than the first reason. The interactive `role finish` names every condition above the `--require-ci` gate and reads the gate only after those pass, so a later `finish` can report a `--require-ci` condition that the first refusal did not name. A matching gate applies its own conditions on top of the declaration. The gate flag is a run input, so no `dispatch` supplies it, a repeat `finish` is refused the same way, and such a run can only end through `abort` with the missing gate named in the reason. `--pr` is an init field, so a later call that changes it is refused, except `declare-pr`, which sets it once on a run that has none, a state file written before the field has no `pr` and keeps the marker-only behavior, and `review-only` refuses `--pr` at init because that mode rejects `--require-ci` at finish. A run that declares no PR keeps the accepted gap of issue #286: the runtime has no PR input, so an omitted `unresolvedCompare` marker still reads as a verified finish (issue #302).
- `--test-cmd <command>` and `--test-cmd-timeout <seconds>` on the init call make the runtime run the command in `--cwd` before each reviewer dispatch, outside the reviewer sandbox, and put the result in the reviewer prompt, in the envelope as `testRun`, and in `lastResult` in the state file. The flag is the only source of the command on every dispatch, a resume included: the state file holds `testCmdSha256`, a digest, and `testCmdTimeout`, only when the run set them, and never the command. Pass the same `--test-cmd` on every reviewer dispatch. A changed value, and a missing value on a reviewer dispatch, are refused before a step is charged. `testRun` is `{ command, status, exitCode, timedOut, durationMs, summary, outputBytes, truncated, tail, workTreeChanged, changedPaths, changedCount, advisory }`, plus `lateChangedPaths` once the reviewer baseline is taken. `status` is `pass`, `fail`, `timed-out`, `slot-timeout`, or `error`. `exitCode` is `null` for `timed-out`, `slot-timeout`, and `error`, whatever code the killed command exits with. The command runs inside a machine-wide test slot (ADR 0040). The slot wait has its own bound, `AGENT_LOOP_TEST_SLOT_WAIT` or 1800 seconds, read on each reviewer dispatch: at that bound the command does not run and `status` is `slot-timeout`, which is neither a pass nor a failure. A slot that cannot be acquired runs no command and gives `error`. A timeout and a cancel kill the command and every descendant that stays in its process group on POSIX, and its tree through `taskkill /T /F` on Windows. Approved limit (repository owner, 2026-10-04, ADR 0017): an orphan that leaves the process group, for example through `setsid`, can survive on POSIX, and an orphan whose parent exited can survive on Windows. The runtime kills no process that it does not own. A canceled command carries `testRun` with `status: "canceled"` on the cancel. A second cancel during the after-command snapshot sets `workTreeChanged` and `changedCount` to `null`, which means not captured. The snapshot still runs after the first cancel. A headless run that ends on a fatal error records it as a `test-run` event in the transcript and prints it in the error report on stderr, so a run with no `--transcript` still delivers it. A reviewer turn that ends in an error still carries `testRun` in the envelope, `lastResult`, and the transcript. The tail is the last 8 KiB of the output, untrusted data, with the values of secret-named environment variables redacted. A command that writes to the work tree is reported in `workTreeChanged` and `changedPaths`, and those writes are not a reviewer mutation, because the mutation check takes its baseline after the command. `lateChangedPaths` lists, at most 20, the paths that differ between the after-command snapshot and the reviewer baseline. It reports a write by a process that the command left behind, made between the two snapshots. That write is in the baseline, so it never halts the run with a `MutationError`. The reviewer prompt shows it. The field is advisory. It is `null` when a second cancel ended the after-command snapshot, and it is absent when the turn ends before the baseline, for example on a cancel of the command. The runtime redacts and bounds `changedPaths` and `lateChangedPaths` in the same way. A turn with no command carries no `testRun`.
- `--reviewer-sandbox read-only|workspace-write` on the init call sets the sandbox of each Codex reviewer dispatch ([ADR 0038](https://github.com/andromarces/agent-loops/blob/main/adr/0038-run-the-codex-reviewer-with-no-sandbox-by-default.md), which partially supersedes [ADR 0019](https://github.com/andromarces/agent-loops/blob/main/adr/0019-opt-in-workspace-write-sandbox-for-the-codex-reviewer.md)). With no flag, a Codex reviewer dispatch runs with no sandbox (`sandbox_mode="danger-full-access"`). `--reviewer-workspace-write` stays as an alias of `--reviewer-sandbox workspace-write`. In the sandboxed modes the shell commands that the sandbox runs have network off. A user Codex execpolicy rule that allows `bash -c`, `sh -c`, or `zsh -c` is an exception, as ADR 0019 states. The flag needs `--reviewer codex`, and any other reviewer is refused at init before a state file is written. The rules for the init field are:
  - The state file holds `reviewerSandbox` (`none`, `read-only`, or `workspace-write`) for a Codex reviewer only.
  - A later call can omit the flag, which reads the stored value, or repeat the stored value.
  - A call that passes another value is refused with `cannot be changed after init`, in either direction.
  - A `reviewerSandbox` that is present but not one of the three modes is refused by `dispatch`, `--resume-interrupted`, `extend`, and `finish`. `abort` ends the run anyway, because it runs no reviewer turn.
  - A state file from before ADR 0038 has no `reviewerSandbox`. It gets `workspace-write` when it holds `reviewerWorkspaceWrite: true`, and `read-only` otherwise, never `none`.
- Two opt-in finish gates apply to `work-first` and `review-first`. `--require-accept` refuses a `finish` unless the latest turn is a reviewer `verdict: accept` with a `Checks` line and the current exact snapshot has the reviewed `head` and `digest`. `--require-ci <pr>` refuses unless the PR head equals the reviewed `head`, the reviewed tree is clean, the PR is not behind its base under a strict rule, has no merge conflicts, GitHub reports a known and unblocked merge state, and every required check passed on the commit GitHub evaluates. Each refusal names the failed condition. In `review-only`, a flagless `finish` keeps the current behavior and each gate fails with a clear error. The source classes, the no-required-check pass, and the Free-plan limit are in [Finish gates](finish-gates.md).
- Live verification of the classic-protection absent-check refusal with a non-admin `GITHUB_TOKEN` is recorded in [PR #285](https://github.com/andromarces/agent-loops/pull/285). The disposable probe repository was deleted after [issue #296](https://github.com/andromarces/agent-loops/issues/296); the recorded result does not depend on it.
- The reviewer prompt carries a fixed review scope on every turn, so a parent prompt that restates the spec does not hide a weakened guard. A weakened existing guard or documented contract stays a blocker, and a finding that is not a defect against the task, not a weakened guard or contract, and not a regression from the base branch goes in `Notes`, not in `Blockers` (issue #1073). When the task names a pull request, the reviewer reads `gh pr checks <pr> --required` for the reviewed head, and a run that declares `--pr` also gets a runtime-read status before each reviewer turn. The status is advisory evidence, never a verdict. The rules are in [Reviewer check status](reviewer-check-status.md).
- The reviewer closing block tells the reviewer to state each blocker concretely in the `Blockers` line and never to point at text outside the block, for example "the defects above". The parent reads only the closing block, so a pointer leaves the worker without the defect (issue #434). The block keeps its one-line, no-list format.
- The worker first-turn prompt has the same rule for every result the parent needs, such as findings, drafts, decisions, and open questions: each stands in full inside the closing block, and the worker never points at text outside it, for example "the decisions above" (issue #976).
- The reviewer is required to end with one explicit `Verdict:` line (`accept` or `reject`, parsed case-insensitively) inside its closing block. The verdict word alone, the word closed by a sentence period (`reject.`), or the word followed by a separator and a trailing clause (`reject — the state does not pass`) parses to that word, unless the clause names either verdict as a whole word. Any other malformed value, including a missing line or a line that names both verdicts, yields `verdict: unknown`; process success never implies acceptance.
- `--transcript <file>` appends one JSON line per `invocation` and `result` event, in the same shape as the headless mode, accumulating across calls. It stays a per-call flag; the `turns` array above is the history every run keeps without it.

Stdout carries exactly one JSON envelope, except for `role --help` and `role -h`, which print plain usage text and exit 0. All logs go to stderr.

A string error message prints unchanged. A message of `null` or `undefined` is not serialized. The error is then the text of the whole error value, for example `Error: null` for an `Error` and `[object Object]` for a plain object. Outside a handled child error, any other message value serializes once under the key `error`, exactly as the envelope serialized it before. Its JSON type and its `toJSON` redaction are kept, and a state file that records the result holds the same value. A message that serializes to `null`, such as `NaN`, `Infinity`, or a `toJSON` that returns `null`, then prints JSON `null`.

A value that cannot serialize, or that serializes to nothing (a function, a Symbol, or a `toJSON` that returns `undefined`), prints a fixed text instead. The fixed text is `[unserializable message]`, or the digits of a BigInt. The envelope therefore never fails to stringify, and an error envelope always carries `error`.

A handled child error result carries text, not a JSON value. A non-string value that the serialization yields prints as its JSON text, so `null` prints the string `"null"`. A string value, such as one that a `toJSON` returns, prints unchanged. A handled child error that timed out prints `<role> timed out after <seconds> seconds` instead of its message.

A message that throws when read prints `Unreadable error`, except for a handled child error that timed out. Before the child turn starts, a message that throws a canceled error prints `Interrupted by SIGINT` instead. Only a message that throws after the child turn starts ends with a recorded result in the state file.

If the stdout write itself fails, for example on a closed pipe, no envelope can be delivered. The command then writes `Failed to write the envelope to stdout: <code>` to stderr. It exits 1 when the command outcome was exit 0, otherwise it keeps that non-zero exit code:

```json
{
  "role": "reviewer",
  "status": "ok",
  "report": {
    "conclusion": "...",
    "why": "...",
    "blockers": "...",
    "checks": "...",
    "notes": "...",
    "deferred": "..."
  },
  "verdict": "accept",
  "reviewed": {
    "head": "...",
    "clean": true,
    "exact": true,
    "digest": "..."
  }
}
```

`report` is parsed from the closing block every child turn must end with. `conclusion`, `why`, and `blockers` are required; `checks` (the commands that ran and their results), `notes` (non-blocking findings), and `deferred` (out-of-scope items) are optional, and an omitted or empty label yields `null` for that field without making `report` null. Every child turn is asked for a `Checks` line, for a worker turn and a reviewer turn alike (issue #310), but only the reviewer `Checks` line is a gate input, so a worker `Checks` line is reported evidence and never an accept. Each label takes one line, plain at column 0. A `- ` list or an ordered `N. ` list (a `-` or a number and a period at column 0, exactly one space U+0020, then the item) that directly follows a report label line is that label's value, or joins the value that line already holds: the markers drop and the items join into one line with `; ` (issues #846, #879, and #915). A list under `Blockers: none` therefore reads `none; <item>`, never `none`. The reviewer `Verdict:` line is no report label, so a list after it stays unparseable. One nesting level folds too: a sub-item line (spaces up to the column where the parent item text starts, so two after `- ` and three after `1. `, then a hyphen, one space, then the item) after a `- ` or `N. ` item joins into that item with `, `, and several consecutive sub-items under one parent all fold into it (issues #870 and #915). An indented non-list line (ASCII spaces or tabs, then text) directly after an item or its sub-items folds into that item with a space, like a Markdown lazy continuation (issue #1082). An indented line never folds when it reads as a label line: after NFKC normalization, it skips every leading character that is no letter or digit and one optional number, then holds a report label name or `Verdict`, any case, optional whitespace, and a character that is no letter, digit, or whitespace. Any colon variant (`:`, `：`, `∶`), any other separator, and any count or kind of markup around the name then refuse, so the items after it stay unparseable lists. A label word that a letter follows (`Notes about x`), or whitespace and then a letter (`Why this matters:`), is prose and folds. An indented list line there stays unparseable too. One prose shape folds too: a blank line after the label line (or after its folded list), then one plain prose line, then a `- ` list directly under that line (dash items only: an ordered list there stays unparseable). The prose line must not start with whitespace (a nonbreaking or ideographic space counts), `*`, `_`, a backtick, `>`, or `#`, must not be a list, and must not hold a report label name or `Verdict`, in any case, followed by any run of `*`, `_`, or backtick marks (or none), whitespace (or none), and a colon, anywhere in the line. The prose and its list join the value of the label just above as `; <prose>: <items>`, the prose losing a trailing colon first (issue #898). A `- ` item or sub-item that opens with a bold report label name (`- **Notes:** ran`) inside such a run is item text and does not blank the block (issue #1006). Any other list in the closing block, for example bullets after the reviewer `Verdict:` line, a list outside any label, a list that a blank line or prose separates from its label outside that shape, a `*` line, a decorated or malformed label, or a `Verdict` line above a list, a bullet with no space after the marker or a separator other than one space (a tab, a nonbreaking space, two spaces) even under an empty label, a `*` or `+` bullet, an `N)` item, an ordered item that a blank line or prose separates from its label, a bold heading line that groups a `- ` list with no label directly above it, a `- ` item that opens with a bold report label name outside a list run under a label, an indented bullet that is not one nested level (no parent item, a second level, another indent width or marker), an indented label, or a decorated label makes the whole block unparseable, so `raw` carries the text instead of dropping it. This covers a label occurrence that a later repeat shadows, which also drops a list that the repeat shadows. A non-list line, for example a closing sentence, does not make the block unparseable. A `*` line is not always a list: a `*` line whose closing `*` a letter precedes, where the character right after the close is not a word character or `*`, and where nothing glued from that character on is a letter or an ASCII digit (`*file*`, `*glob src/a*`, `*use a* b`), reads as an emphasis run, so a spaceless `*` bullet of that shape is an accepted gap. The block still parses and every matching line drops with no `raw` signal, the same as any other line that is neither a label nor a list, because the bullet text and the emphasis text are the same bytes. Every other `*` line either is a list and blanks the block, for example `*item`, `* item`, or `*file*.mjs`, or is not a list and drops as prose, for example `**bold** note` (issue #275). When parsing fails, `report` is null and `raw` carries the whole response. `status: "error"` carries `error`, and every error path still prints one JSON object. The subcommand launches no orchestrator model and accepts no `--orchestrator` flags.

A reviewer envelope carries `reviewed`: `{ head, clean, exact, digest }` from the snapshot the runtime takes before the reviewer turn, so the child cannot misreport it. A reviewer turn in a run that named a PR, with `--pr <pr>` or with `--require-ci <pr>` on the headless command, also carries `prChecks`: `{ pr, head, status, checks, summary, advisory }`, the required-check status the runtime read for that PR head before the turn, where `status` is `pass`, `failing`, `pending`, or `unresolved`, `checks` names the checks in that state, `head` is the commit the status describes, `advisory` is always `true`, and `summary` is the one-line form the reviewer prompt carries. The state file keeps the same `prChecks` beside the response in `lastResult`, so a parent can compare the runtime read with the reviewer `Checks` line. The read resolves the PR head and reports a status only when it matches the local reviewed head. It reads the check runs and commit statuses of that commit by SHA, every page of each, so a head that moves away and back during the read cannot change what the status describes. A mismatch, a failed read, a reply or an entry that cannot be parsed or ordered, a classic protection reply that cannot be interpreted, a failed read of the required names, an unreadable ruleset source, a base branch with no required check, and a stalled read are all `unresolved` and never a failed turn. `advisory` is always `true` because the status is a report, and the `--require-ci` finish gate re-reads GitHub and enforces the condition. The status is a snapshot taken before the turn, so a check that starts or finishes later is not in it. A run that names no PR carries no `prChecks` (issues #320, #350). `head` is the commit, `clean` is true when the work tree has no uncommitted entries, `exact` is true when every entry has a content hash or is a deletion, and `digest` identifies the uncommitted state. A symlink hashes its link target text with a tag, so two links with different targets have different digests, dangling included, and a link never collides with a regular file that holds the same bytes.

The `finish` envelope is `{ "status": "ok", "lifecycle": "finished" }`, and the command exits 0. A finish that recorded an unresolved PR-head compare adds `"unresolvedCompare": true` and still exits 0, where the headless loop exits 4 for the same condition, and a verified finish keeps the envelope unchanged. `finish --compare-head <pr>` reads the PR head and state and refuses unless the PR is open, its head equals `reviewed.head`, and the reviewed tree is clean. A closed or merged PR refuses even when its head is unchanged. It reads no required-check source, so it serves a repository whose required-check sources cannot be read. It adds `"headCompare": "verified"` to the envelope and the state file, distinct from `unresolvedCompare`, and is refused with `--require-ci`, with `unresolvedCompare`, and for a run that declares a PR (#1098). A finish whose summary holds a key other than the five summary keys and `unresolvedCompare` is refused, names each unknown key, and leaves the lifecycle `active`; the headless `finish` action applies the same rule to its own keys and its summary (#1021).
