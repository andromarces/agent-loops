# `wait-checks`

Part of [Child dispatch](role.md). The orchestrator rules for the command are in [Waiting for required checks](../orchestrator/waiting-for-checks.md), which also holds the retry, paging, and `Link` host rules of its reads.

Usage: `agent-loop role wait-checks --pr <pr> [--all [--expect <check name>]...] [--head <sha>] [--cwd <dir>] [--timeout <seconds>]`. It prints `{"status": "ok", "pr": 42, "timedOut": false, "head": "<sha>", "checks": [{"name": "ci", "state": "SUCCESS", "bucket": "pass"}]}`.

## Check states and failures

`head` names the commit that `checks` describe. `gh pr checks` queries by PR identity and names no commit, so the wait never takes a check state from it. Each poll reads the PR head `<sha>` and the base branch with `gh pr view <pr> --json headRefOid,baseRefName`, runs `gh pr checks` for its exit-code outcome, and reads every state from the check runs and commit statuses of `<sha>` by SHA (`repos/<slug>/commits/<sha>/check-runs` and `.../status`, every page, read together). The required wait judges each required context as the `--require-ci` gate does, with the gate's own matching and verdict: the contexts come from `requiredContexts` (repository rulesets with `integration_id`, classic protection with `app_id`, and the names `gh pr checks --required` lists), an app-qualified context is satisfied only by a check run of that app, the latest matching entry decides, and a context with no entry on `<sha>` is pending. The `--all` wait judges the latest check run of each name and app and the latest commit status of each context. A head that moves away and back, or a stale view, therefore cannot put another commit's checks under `head`. The states of `<sha>` only make the outcome stricter: a failing state of `<sha>` settles the wait, and a pass needs both the `gh pr checks` outcome and every state of `<sha>` to pass, so exit 8 or the no-check-yet reply keeps the wait running while `<sha>` shows a pass, until the bound ends it with `timedOut: true`. A failure that `gh pr checks` lists settles the wait whatever `<sha>` shows, and it is reported in `prFailures`, apart from `checks`, because it is PR-level evidence that is not pinned to `<sha>`: `checks` holds only states read for `head`, and a parent never records a pass from an envelope that carries `prFailures`. `prFailures` appears only when `gh pr checks` listed a failure in the last poll, and it survives a bound that a later read reaches and a commit or source read that fails (`head: null`, empty `checks`).

## Required contexts

The required wait refuses a context it cannot resolve, with the rule of the supplied status (`requiredResolutionRefusal`): a ruleset or protection source that cannot be read, a source reply that cannot be parsed, and a failed read of the required names each exit 1 with `status: "error"` before any state is judged, because such a source can hold a required check or an app qualifier that the wait never saw; a listed failure still settles the wait then, and the `--all` wait reads no source. A commit read that fails, or that returns a reply the wait fails to parse or order, is an error too, with one exception.

The reads page and retry as [Waiting for required checks](../orchestrator/waiting-for-checks.md) states: no read follows a reply-supplied `Link` URL (#1033), a 500, 502, 503, or 504 is retried on the next poll inside the bound (#1025, #1121, #1125), and the `--require-ci` finish gate keeps failing closed on every read failure. A successful paged read joins the pages into the array that the earlier slurped read printed.

## Bound and head

`--head <sha>` takes a full lowercase commit SHA of 40 or 64 hex digits, refuses an abbreviation, and is refused on every other operation: while the PR head is another commit the wait reads no checks and continues, and a wait that reaches the bound first returns `timedOut: true`, `head: null`, and an empty `checks`, never a pass. `head` is `null` only when no read completed (issue #961). It reads status only, so it writes no run state and needs no init, and it returns inside its own bound: `--timeout` is in seconds, defaults to 300, and refuses 0. The runtime owns the bound because `gh pr checks --watch` takes no timeout and a shell `timeout` is absent on Windows and on macOS without GNU coreutils (issue #329). The bound covers the whole command, not only the reads: it starts at command entry and no step of the command adds time to it. Work-tree validation runs inside the bound, with `assertGitWorkTree` carrying the remaining time to `execa` as `timeout` with `cleanup` and `killDescendants`, so a slow or hung `git` is terminated and a validation that reaches the bound refuses, because a work tree the probe never confirmed is not one the command may read. Every read is limited to the time the command has left, and a read that reaches the limit is stopped and then given five seconds to exit, so the total bound is `--timeout` plus five seconds. The `gh` child is terminated on expiry the same way: `SIGTERM` then `SIGKILL` after one second on macOS, and `taskkill /T /F` over the process tree on Windows. `timedOut: true` means the bound was reached, whether with a pending check or during a read; it is a completed read, and the envelope carries the last check states that were read, so an empty `checks` with `timedOut: true` means no check state was ever read. `childExitUnconfirmed: true` appears only when the five-second ceiling expired with the `gh` child still unaccounted for: the command does not claim an exit it did not observe, and a parent that sees it settles the outstanding `gh` process before starting another wait.

## Exit codes and the no-required-check answer

The `gh pr checks` exit codes decide the outcome as the reviewer read states them: exit 0 with no pending check listed is settled, exit 8 is pending, and exit 1 is settled only when the output lists a failing required check, or when `gh` prints exactly `no required checks reported on the '<branch>' branch` and no output. Any other exit 1, and any output that is not a check list, exits 1 with `status: "error"` and no check state, so an unresolved read never reads as a pass. Every check item is read as a name plus a `state` or `bucket` the CLI knows; an item carrying no readable state is unresolved, so one item the CLI cannot read cannot settle the wait as a pass. A check that has not started is absent from `checks`, because the command omits it, so an empty list means no required check has reported and the wait continues. That answer, matched with the pattern of the required-check gate, and only when the ruleset and classic-protection sources each state the absence as the gate decides it, exits 0 with `"noRequiredChecks": true`, an empty `checks`, and `"timedOut": false`: it is not a read error and never a pass, and the parent dispatches the reviewer, which reads the CI status itself (issue #894), after one `wait-checks --all` run. The same `--all` run follows the required wait's refusal that no required-check source can state the required checks (the Free-plan 403 of #301, a source that `settled nothing`, `could not be read`, or `did not state that it holds no required check`): it is never a required-check pass, and a reply that could not be parsed or a failed read of the required names stays an unresolved read with no `--all` run (issue #1018). Measured live on 2026-10-17 (Windows 11 Pro 10.0.26220, `gh` 2.102.0, Node v26.8.1) on a pull request of a private GitHub Free organization repository with no required check: the required wait exited 0 with `{"status":"ok","pr":265,"timedOut":false,"noRequiredChecks":true,"checks":[]}`, and the following `--all` wait exited 0 with `{"status":"ok","pr":265,"timedOut":false,"checks":[{"name":"checks","state":"SUCCESS","bucket":"pass"}]}`.

## `--all`

`--all` runs `gh pr checks <pr> --json name,state,bucket` with no `--required` for the same exit-code rules, and judges the check runs and commit statuses of the commit `head` names, with the same bound. Because it has no required-check answer, an exit 1 with no failing check listed is unresolved, including `no required checks reported on the '<branch>' branch`, and `noRequiredChecks` never appears in its envelope (issue #896). The one exception is the exact `no checks reported on the '<branch>' branch` reply with no output: it is an empty list, so the `--all` wait continues as the required wait does, and at the bound it returns `timedOut: true` with an empty `checks`, never a pass. A repository with no CI workflow therefore waits the full `--timeout` (issue #950). `--all` is refused on every other operation.

## `noCheckSource`

The `--all` wait ends that wait at once with `noCheckSource: true`, `timedOut: false`, and an empty `checks` when its first read lists no check, no `--expect` name is set, the read of the PR head by SHA finds no check run and no commit status, and no source can report a check for the PR head: the PR changes no file under `.github/workflows/` (`pulls/<pr>/files`, every page, `previous_filename` included), no workflow file of the base branch (`contents/.github/workflows?ref=<base SHA>`, then each file) names `pull_request`, `pull_request_target`, `push`, `merge_group`, `workflow_run`, or `check_suite` in its text (a file that names them counts as unable to report only under the path-filter rule below), and neither the base head nor the head of the latest merged PR of that commit has a check run or a commit status. The merged PR comes from `commits/<base SHA>/pulls` (the pager of the commit reads): the entries merged into the base branch with the latest `merged_at`, whose head SHAs the probe reads like the base head. PRs that share the latest merge time are all read, so a check on any one keeps the wait and the list order never decides. A PR on that commit that is not merged or targets another branch is no evidence, and no merged PR adds no read. Every entry must be exact, or the wait stays: `merged_at` null or a real UTC timestamp (`YYYY-MM-DDTHH:MM:SSZ`), `base.ref` a valid Git branch name (the rules of `git check-ref-format --branch`, so a blank, padded, or `..` name keeps the wait), `head.sha` a lowercase full SHA (#1062).

The base branch resolves to one SHA first (`commits/<base>`), every base read uses it, and a base branch or PR head that moved by the end keeps the wait. A missing workflow directory (the exact `Not Found (HTTP 404)` reply) counts as no workflow. Each read is bounded by the wait. The PR files use the pager of the commit reads, and the single reads (`readOne`) share the validation of that pager (`readReply`): the `Link` host check of every reply (#1033), the first-line status, a 2xx status block, one JSON value, and the 5xx retry classification (#1025), and a success with a `Link` header is refused. A missing workflow directory is only the exact 404 reply: a 404 status line, exactly `gh: Not Found (HTTP 404)`, a JSON body, and no `Link` target. A workflow file needs `type: file`, well-formed base64 whose bytes equal `size` and are valid UTF-8, and no backslash or control character in its text, because a YAML escape can spell an event name. A read that fails, cannot be parsed, has another shape, or is at an API cap (3,000 PR files, 1,000 directory entries) keeps the normal wait.

A workflow file that names a trigger still counts as unable to report for the PR when the whole file parses as exactly one YAML document with the `yaml` package (the only parser of the project, with `uniqueKeys` on and aliases off), with no error and no warning, and its top-level `on` map names only `pull_request` and `pull_request_target`, each with a non-empty `paths` list, and no PR file (`previous_filename` included) matches any pattern under the GitHub filter rules. A pattern is a string of letters, digits, `_`, `.`, `-`, `@`, `/`, and `*` with no empty, `.`, or `..` segment. `*` stays inside one path segment and `**` crosses segments and matches any character, a newline included; a pattern with no `*` also matches the files under it, and the match is case-insensitive, which can only keep the wait. The wait stays when the file names any other event (`push`, `workflow_dispatch`, and the rest), a PR event has no `paths` list or an empty one, the file uses `paths-ignore`, a pattern holds any other character (a `!` negation, `?`, `+`, `[...]`, so the matcher never needs those translations), the text has a syntax error anywhere (for example a later `jobs: [` or an unterminated `branches: [main`), a second document, a duplicate key, a tag on any node (`!!str` and `!!map` included), an anchor, an alias, a second `on` key, or any other parser warning, a PR file name is not a string or holds a control character, a line or paragraph separator, or a lone surrogate (GitHub documents no rule for such a name), or the file list is incomplete. The limit: the check is YAML syntax, not the schema of GitHub Actions, so a well-formed file that GitHub rejects for another reason still counts, and the `branches` and `types` filters of the event are ignored, which only keeps the wait (#1065).

The envelope is never a pass: the parent dispatches the reviewer, records the CI status as not verified, and reads no workflow itself. The limit is that the base head and one merged PR head are two commits (the latest merge time, ties included), so a provider that skipped both, that registers later, or that reports on a base head with no merged PR (a direct push) stays unseen (issues #1054, #1062).

## `--expect`

`--expect <check name>` (repeatable, needs `--all`, refused on every other operation) keeps the `--all` wait running until each named check has a check run on `<sha>`. A name matches the name of a check run exactly: it is trimmed, case-sensitive, and any app qualifies, and a commit status of that name never matches. An empty name is refused and a repeated name is accepted. Commit statuses still count in the overall pass evaluation: a check that a third-party app registers after the first ones passed is otherwise absent, so an early pass is not evidence. A name that never registers ends the wait at the bound with `timedOut: true` and the name in `awaiting`, never a pass, and a failing check still settles the wait (issue #978).

`--cwd` must be inside a Git work tree, as it is for `dispatch`.
