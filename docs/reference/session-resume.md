# Session resume

## Session resume after a failed turn

A failed first turn keeps its session. When the CLI reported a session id, the adapter stores it on the role state on every failure path, including a non-zero exit, a timeout, and a response-validation failure such as a missing response text, so the next turn resumes that session and the edits the failed turn left. Each adapter selects the reported id by its own rule, then requires the selected id to be a non-empty string. Claude and opencode take the first truthy id in the output, so an empty id is skipped and a later valid id is used, while a truthy invalid id, such as a number or an object, fails the turn. Codex takes the `thread_id` of its first `thread.started` event, and an empty or invalid one fails. Copilot takes the id of its last result event (`sessionId`, or `session_id` when `sessionId` is null or absent), and an empty or invalid one fails. When a failed Copilot first turn reports no id (absent or null, not an invalid one), the adapter keeps the pre-assigned id with `sessionUnconfirmed` if the session holds a saved turn (see the Copilot row below, ADR 0030). agy reads the `conversation_id` of its one result object, and an empty or invalid one fails. A failed selection stores nothing on a first turn and leaves a resumed turn with its stored id. In every adapter except agy, a resumed turn whose selected id differs from the stored id raises `resumeMismatchError`. agy has no mismatch check: a successful resumed turn stores the valid `conversation_id` its result carries, and it logs a warning only when stderr matches `conversation "<name>" not found`. A failed turn never changes the id of a resumed session in any adapter. Every adapter except agy keeps the resumed id or raises `resumeMismatchError` on a different one. agy adopts the `conversation_id` that its successful result carries, even when it differs from the resumed id, and logs a warning only when it resumed an id and stderr matches `conversation "<name>" not found`. A resumed agy turn is sent without the role preamble, so a new conversation that agy started has not received it. The Claude adapter refuses a different id from a resumed turn, as Codex, Copilot, and opencode do. A Claude first turn passes a pre-assigned UUID with `--session-id` and keeps it when the turn fails, unless the failed output reported another id, which wins. A kill that leaves stdout empty therefore keeps the id. Claude Code 2.1.292 probe, with the same prompt shape each time: (1) a first turn killed with SIGTERM 30 s into a `sleep 90` tool call printed nothing, wrote its session file, and `--resume` of the pre-assigned id answered with the earlier command in its history and echoed the id; (2) a first turn killed 0.4 s in wrote no session file, and `--resume` of its id exited 1 with `No conversation found with session ID: <id>` and empty stdout, so the next turn reaches the missing-session fallback below and reruns once as a first turn with a new pre-assigned id. A successful first turn adopts the id the CLI reports and logs a warning when it differs from the pre-assigned one. A resumed turn passes no `--session-id`. On the interactive `role dispatch` path, the adapter reports the pre-assigned id before it starts the CLI and the dispatcher writes it to the state file at once, so a parent crash during a first turn leaves the id, and the first turn after `--resume-interrupted` resumes that session. If the CLI never saved the session, that resume reaches the missing-session fallback. A failed write stops the turn before the CLI starts. A first turn that the CLI rejects with `Error: Session ID <id> is already in use.` (exit 1, empty stdout, that one line byte for byte, optional LF or CRLF; Claude Code 2.1.292) never keeps the id: the id names another session, so the state file records null and the next turn starts with a fresh id. The rejected turn is not rerun and charges its step. The adapter withdraws the id through the same callback as soon as it sees that rejection, before it rethrows, so the state file holds no rejected id while the turn ends. Only a crash in the instant between the rejection and that write can still leave it. The state file also marks a pre-assigned id `sessionUnconfirmed` until the CLI output reports the session, because an unrelated session of another work tree can hold the same UUID and `resumeMismatchError` cannot catch it: that session reports the same id. Before the adapter resumes an unconfirmed id, in crash recovery, after `--continue-from`, or on the next turn, it requires a Claude Code session file `<id>.jsonl` under `$CLAUDE_CONFIG_DIR/projects` (default `~/.claude/projects`) whose first user record names the id and this work tree and carries the marker `[agent-loop session <id> role <role>]`. The adapter appends that line to the prompt of every first turn. The id is a fresh random value that only the state of this run records, and the role is part of the marker, so another session in the same work tree, a session of another role, and a session of another id never match. Only the marker match reads session content, from the first 256 KiB of the file, and nothing of it is logged. An id that is not a canonical lowercase UUID is refused before any path is built. A symlinked project directory or session file is not followed, and only a regular file counts. `--continue-from` restores the `sessionUnconfirmed` mark with the id from the transcript, and a transcript whose mark is not a boolean is refused. An id that fails the check raises the missing-session error before any CLI starts, so the runtime clears it and reruns the turn as a first turn with a new pre-assigned id, with the preamble and no second step. A session store elsewhere reads as not owned. The headless loop does the same when `--transcript` is set (issue #564), for a Claude orchestrator, worker, or reviewer: it rewrites the transcript before the CLI starts, with the id and `sessionUnconfirmed` on that role, so a parent crash during a first turn leaves a transcript that `--continue-from` resumes after the ownership check. A rejected id is withdrawn the same way. The written file keeps that id until the next transcript write, so a crash during the turn leaves it on disk. The id is held in an in-memory overlay that the end of the CLI call clears, and the role state is not changed. The next write, at the latest the write at exit, records what the adapter decided: an id that the output reported, else the pre-assigned id with its mark, else none. Three limits apply. A failed transcript write only warns, as at exit. A run with no `--transcript` keeps no record, so a crash there still loses the id. The mutation check of an orchestrator or reviewer turn covers the whole Git work tree (the repository root, not only `--cwd`) and has no exemption. A transcript inside that tree therefore cannot be written during those turns. For those two turns the loop writes a session record outside the tree, `<tmpdir>/agent-loops/session-records/<key>.json`. For a transcript inside the tree, the loop also writes the transcript once before the first turn. That write adds `runNonce`, a random UUID of the run. The record has exactly eight fields: `version` (always 1), `transcript` (the key), `cwd`, `runNonce`, `transcriptSha256`, `role`, `sessionId`, and `sessionUnconfirmed` (always `true`). `transcriptSha256` is the digest of the transcript file that the loop wrote last. The record holds no task text. `--continue-from` ignores a record unless five tests pass. The record is a small regular file of the current user. It has exactly those fields. The id and the nonce are UUID strings, and no other type passes. It names this transcript and work tree. Its `runNonce` equals the one in the transcript. Its digest equals the digest of the transcript now. Every later transcript write removes the record and makes an older one stale. A valid record gives the id and the unconfirmed mark to a Claude role that has no id. The ownership check then always runs before the id resumes (ADR 0027). The third limit is a lost record. A clean-up of the temporary directory removes it. If the temporary directory is inside the work tree, the loop saves nothing before an orchestrator or reviewer turn and logs a warning. A refused ownership check on a resumed orchestrator id ends the run and keeps the id with its mark, because the orchestrator has no first-turn rerun, so the next `--continue-from` checks the id again. The restore runs inside the mutation check, so a failed snapshot after the turn cannot lose the mark. Not verified: the behavior on a Windows file system (path case, junctions, and rename over an open file), and the transcript left by a real process kill. The tests simulate the kill by reading the file mid-turn. The worker turn is not under the check and writes. Separate processes that share one transcript path have no write coordination: each write is atomic, and the last one wins. The Copilot adapter keeps the id that the result event of a failed first turn reports. When the output reports no id, it keeps the pre-assigned id with `sessionUnconfirmed` only if the session holds a saved turn (a `user.message` event in `events.jsonl`, see the Copilot row below and ADR 0030), because a failed turn that saved no turn leaves a session that holds nothing, and a kept id would skip the preamble for nothing. An id that the output reports but that is empty or not a string stores nothing. On Copilot CLI 1.0.90-4, a first turn that failed on a bad model printed no result event, and a later call with the same pre-assigned id completed and echoed that id. Issue #642 showed on Copilot CLI 1.0.96-2 only that a bad-model failure saves no turn. The 1.0.90-4 run did not check the session files, so that it behaved the same there is an inference. On 1.0.95, a call with the id of a successful first turn resumed that session.

When a resume fails because the CLI has no such session, the Claude and Codex adapters mark the error, and only for exit 1 without a timeout, cancel, or signal, with empty stdout and stderr that is the one verified line for the requested id, byte for byte, followed by at most one line ending (LF or CRLF). That line ending is the only normalization: leading or trailing spaces, blank lines, a second line, or any other text leave the error unmarked, so a real failure is never rerun. The runtime then clears the id and reruns the turn once as a first turn: a worker gets the role preamble again. The rerun charges no second step. The failed resume ran no model turn, so the step pays for the one requested turn, and the rerun happens at most once per turn. The transcript shows two `invocation` events with the same `stepsUsed`, and the state file keeps one `turns` entry (issue #360, ADR 0016).

### `claude`: resume after a kill

A resume of an unconfirmed id first needs a session file that this work tree and role own. On Windows 11 (Claude Code 2.1.295, issue #565): the file is `projects/<cwd with each non-alphanumeric character replaced by "-">/<id>.jsonl`, its first `user` record has `sessionId`, `cwd` as spelled at launch, and `message.content` as a string, the CLI keeps the case of the id that it is given, a `cwd` that differs only in the case of the drive letter is read as the same work tree (`realpath` returns one spelling), a junction as the project directory is refused, and a forced terminate (`taskkill /F /T`) before about 3 s leaves no session file, so the check refuses, a worker or reviewer turn reruns as a first turn, and an orchestrator turn ends the run and keeps the id with its mark, while one after about 3 s leaves a file that passes the check and resumes. On macOS 27.2 (Claude Code 2.1.296, issue #580), `SIGKILL` and `SIGTERM` sent to the headless parent pid gave the same results: the id and its mark stay, `--continue-from` resumes them after the ownership check when the session file exists, and a run whose sample showed no session file gives the refusal for an orchestrator id and a rerun as a first turn for a reviewer id. A check 1.5 s after the parent exit found no `claude` child after `SIGTERM`, and a `claude` child with parent pid 1 after `SIGKILL` in 12 of 14 probes. Issue #565 repeated the probes on macOS 27.2 (Node v26.11.1, Claude Code 2.1.296). The file layout, the first `user` record fields, and the case of the id match the Windows result. A `SIGKILL` of the `claude` process at 0.4, 1, and 2 s left no session file. The check refused, and `--resume` exited 1 with the line above. A `SIGKILL` at 2.5 to 30 s left a file that passed the check and resumed. A `SIGKILL` of the headless parent at 0.4 s ended the continued run with the refusal. At 1.5 s and 3.5 s, the continued run resumed. A file symlink and a directory symlink were refused. These symlink probes ran against a synthetic session store with a stub `claude`, not against real sessions. ADR 0016 holds the commands and the output. Linux, the Windows symlink cases, and a real-session symlink probe are not verified.

Issue #398 probed a session id read from the output after a kill, on macOS 27.2 with Claude Code 2.1.296. The first command was `claude -p --model haiku --allowedTools Bash --output-format stream-json --verbose`. `SIGKILL` went to the `claude` process 4 s after the `Bash` `tool_use` event of a 64 s `node` timer. The first `system` `init` event printed the `session_id`. The resume command was `claude -p --model haiku --resume <id> --output-format json --verbose`.

The resume exited 0. Its `init` event and its `result` event carried the same id. The answer named the word of the first prompt. It said that the timer result was not recorded. The `zsh` shell of the `Bash` call and its `node` child stayed alive after the kill, with parent pid 1.

The adapter uses `--output-format json`, which prints no id before the end. The adapter relies on the pre-assigned id. No result contradicts the adapter.

Issue #675 repeated the kill under `--output-format json` on macOS 27.2 with Claude Code 2.1.296. `SIGKILL` went to the `claude` pid 4 s after a 64 s `node` timer started, and stdout and stderr stayed empty. A direct CLI resume with `--resume <id>` exited 0, with the same id in its `init` and `result` events. The probe prompt carried no ownership marker, so it does not show the adapter recovery path, which issues #565 and #580 cover. The Linux and Windows Claude cases stay unverified, because no host of either kind was available (issue #675). ADR 0016 holds the commands and the decisive output.

### `agy`: resume of a missing session

The adapter stores the valid id the result carries. When that id differs from the resumed one, with or without the stderr text, the adapter logs a warning. It also marks the state `conversationReplaced`. A resumed turn carries no preamble.

For a worker, the runtime then runs one preamble-only turn in the new conversation, in the same step. It never reruns the task, so its edits are not repeated. Limits: the task prompt reaches the new conversation before the preamble. The preamble-only turn can still write, because a worker turn has no mutation check. A failed preamble turn only warns. The preamble-only turn carries the `Init task:` block with the preamble. A reviewer has no such turn. Its next turn carries the block, because `taskSentTo` names the old conversation.

An orchestrator turn is read-only. The runtime reruns it once with the initial instructions before the same prompt. The earlier orchestrator turns are lost. Each of the two calls has its own mutation check, so an edit that the rerun restores is still detected.

A cancel after the replacement ends the turn as canceled. This includes a cancel in the preamble-only turn or the rerun. The turn keeps the id the CLI reported (ADR 0027) and leaves `conversationReplaced` set on the role. The next worker turn then sends the preamble with its task. The role state also keeps `taskSentTo`, the id of the conversation that last carried the init task. The next worker turn sends the preamble without the `Init task:` block when `taskSentTo` names the session it resumes. The replaced conversation then sees the task at most once. A canceled turn that carried the task counts as delivered. If the CLI dropped that prompt, the conversation never sees the task. A reviewer conversation that a resumed turn replaces gets the task only on its next reviewer turn. A run that ends first leaves that conversation without the task. The reviewer preamble differs: it goes out on every reviewer turn, and the init task does not. The mark is stored in the run state of `role dispatch` and in the `--transcript` roles, and `--continue-from` restores it with the id.

A live probe ran on agy 1.3.2 (issue #579) in a scratch Git repository, with `--input-format text --output-format json` and the prompt on stdin. Probe 1 resumed a missing name and a missing well-formed UUID, both with `--mode plan`. Each exited 0, printed `warning: conversation "<name>" not found` on stderr, and returned `status` `SUCCESS` with a new `conversation_id`. A resume of an existing id, from the same or another work tree, returned the same id and no warning. The probes do not show that a missing id is the only cause of a replaced conversation. No probe resumed a missing id with no stderr line, so tests alone cover that branch.

Probe 2 sent the runtime preamble-only worker prompt to a missing id, with no `--mode`. It answered `OK`. The work tree kept its HEAD and an empty `git status`. One probe does not show that the turn can never write.

Probe 3 sent the runtime rerun orchestrator prompt to a missing id, with `--mode plan`. The prompt held the initial instructions, the restart sentence, and a worker result prompt. It answered `run_reviewer`, the action for the result, not `run_worker`, the first action that the instructions ask for. The same result prompt with no instructions also answered `run_reviewer`, because it names its own action list. So the probe shows that the rerun does not misread the instructions. It does not show that the instructions are needed.

Issue #657 repeated the three probes on agy 1.3.2 on Windows 11 Pro (10.0.26220), on 2026-10-10, in a disposable Git repository in the system temporary directory, with the same flags and prompts. A missing name and a missing UUID each exited 0, printed `warning: conversation "<id>" not found`, and returned `SUCCESS` with a new id. An existing id returned the same id and no warning. The preamble-only worker prompt answered `OK`, with HEAD and `git status` unchanged. The rerun orchestrator prompt answered `run_reviewer`, and the result prompt alone also answered `run_reviewer`. The Windows result matches macOS. No Linux host was available, so Linux is not verified.

No result contradicts the adapter or the runtime.

### `agy`: resume after a kill

The first turn used `agy --input-format text --output-format json --dangerously-skip-permissions`. The prompt asked to remember a word and to run `sleep 63; echo hi`. `SIGKILL` went to the `agy` process 15 s after the start. The conversation transcript shows `run_command` with status `RUNNING` as a background task. Stdout was empty, so the output named no id.

The conversation existed on disk as `~/.gemini/antigravity-cli/conversations/<id>.db`. A second call with `--conversation <id>` exited 0 and returned the same `conversation_id`. It answered `The secret word is PAPAYA, and the sleep command did not finish because the background task stopped during a server restart.`. A kill during a tool call therefore leaves a conversation that resumes. The adapter keeps no id, so it cannot resume it.

With `--output-format stream-json`, the first event (`init`) carries `conversation_id`. The adapter does not use that format. The tool shell stayed alive after the `agy` process ended, with parent pid 1. The kill probe is not verified on Linux or Windows, because no host of either kind was available in issue #675. No result contradicts the adapter. ADR 0016 holds the commands.

### `copilot`: resume of a missing session

A live probe ran on Copilot CLI 1.0.95 (issue #375). It made a first turn with a fresh random `--session-id` and `--output-format json`, then two later calls with the same id. Each call exited 0.

The last event of each call was a `result` event. Its top-level `sessionId` matched the pre-assigned id. The `result` event has the fields `type`, `timestamp`, `sessionId`, `exitCode`, and `usage`. The test mocks carry `type`, `sessionId`, and `exitCode`, so the adapter needed no change. The third call recalled the word of the first message, so a call with an existing id resumes that session.

A first turn failed with a bad model and printed no result event. A later call with the pre-assigned id completed and echoed it. Issue #641 verified that a call with the pre-assigned id of a failed first turn resumes a session that holds the turn when the turn ran a tool (see the last column). No fallback applies to a confirmed id.

Issue #398 repeated the case of a session that does not exist, on macOS 27.2 with Copilot CLI 1.0.96-2. A first call used a fresh random `--session-id` and no earlier session. It exited 0 and answered `NONE` to a question about an earlier message. Its `result` event echoed the id. An id with no session therefore creates a session. No CLI error can trigger a fallback.

### `copilot`: session id of a failed first turn

When the output reports no id (the field is absent or null), it keeps the pre-assigned id, marked `sessionUnconfirmed`, only if the child process started and `<COPILOT_HOME or ~/.copilot>/session-state/<id>/events.jsonl` is a regular file in a real directory, neither followed through a link, whose first 256 KiB holds a `user.message` event (issue #642, ADR 0030). An id that the output reports but that is empty or not a string is invalid, and it stores nothing, with or without a saved turn. A failure before the prompt was recorded, such as a bad model or an unsupported effort, leaves no `events.jsonl` and keeps no id, so the next worker turn carries the preamble. A resume of an unconfirmed id runs the same check first. A session with no saved turn raises the missing-session error before any CLI starts, and the runtime reruns the turn as a first turn with the preamble. A result event or a failed result that reports the kept id clears the mark. Another reported id leaves the kept id and its mark, and the mismatch error follows. A resumed turn never changes its id.

### `copilot`: resume after a kill

Copilot CLI 1.0.95 ran the first probe and 1.0.96-2 ran the second, because the CLI updated itself between them. Each probe used `copilot --session-id <fresh uuid> -s --no-ask-user --output-format json --allow-all-tools`, with the prompt on stdin: remember a codeword, then run `ping -n 60 127.0.0.1 > nul & echo PROBE_TOOL_DONE`. The probe read the stdout events and ended the process tree with `taskkill /F /T` 1.5 s after the first `tool.execution_start` event.

In both probes the first call exited 1, printed a `tool.execution_start` event with no `tool.execution_complete` event, and printed no `result` event. The second call used the same `--session-id` with the prompt `What codeword did I ask you to remember, and which shell command did you run? Answer in one line.` It exited 0 and its `result` event echoed the pre-assigned id. In the 1.0.96-2 probe the reply was `Codeword: ZEBRA933905; Command: ping -n 60 127.0.0.1 > nul & echo PROBE_TOOL_DONE`, which matches the first prompt. In the 1.0.95 probe the reply named the same command and declined to repeat the word, which it called secret. The session file of each probe in `~/.copilot/session-state/<id>/events.jsonl` held two `user.message` events and one `tool.execution_start` event. The resumed session therefore holds the turn that failed after a tool call, and a failure of this kind leaves a session under the pre-assigned id. The result holds for a kill. Issue #642 probed on 1.0.96-2, same host: a bad `--model` and `--reasoning-effort xhigh` on a model that does not support it each exited with an error and no result event, and left a session directory with `workspace.yaml` and no `events.jsonl`. An adapter run of a first turn that the timeout ended after the prompt was recorded (9 s to 13 s) kept the pre-assigned id with the mark, and one that the timeout ended before the prompt was recorded (3 s to 7 s) and the bad-model run kept none. A completed turn wrote `events.jsonl` with `session.start`, `user.message`, `assistant.message`, and `session.shutdown`. A model error in the middle of a model call could not be produced, and its failure ends like a kill with no result event, so the same file check decides it (test only).

Issue #398 repeated the kill on macOS 27.2 with Copilot CLI 1.0.96-2. Each call used `copilot --session-id <fresh uuid> -s --no-ask-user --output-format json`. The tool case also used `--allow-all-tools`. The probe sent `SIGKILL` to the `copilot` process. Each resume used the same `--session-id` and asked for the word of the first prompt.

A kill 3 s after the first `tool.execution_start` event of `sleep 60` left no `result` event on stdout. The session directory held `events.jsonl` with a `user.message` and a `tool.execution_start` event. The resume exited 0 and echoed the id. It answered `MANGO; no, the sleep command did not finish.`.

A kill 2.5 s after the start printed only MCP status events. It left a session directory with no `events.jsonl`. The resume answered `MANGO`. A kill 0.3 s after the start left no session directory. The resume exited 0 and answered `NONE`, so it started a new session under the id.

The result matches issue #641 on macOS. It adds no new contradiction of the adapter. The `copilot` command runs a Node loader that starts the native binary. A kill of the loader pid left the native process and the tool shell with parent pid 1. ADR 0030 keeps the id when `events.jsonl` holds a `user.message` event (issue #642). ADR 0016 holds the commands.

Issue #675 killed the native process instead, on macOS 27.2 with Copilot CLI 1.0.96-2. `SIGKILL` went to the native `copilot` child of the loader pid, 3 s after the first `tool.execution_start` event. The loader exited with code 1, and stdout held no `result` event. The resume with the same `--session-id` exited 0 and recalled the word of the first prompt. The tool shell stayed alive with parent pid 1, which issue #679 probes. No result contradicts the adapter, and ADR 0016 holds the command and the decisive output.

### OpenCode

The OpenCode adapter passes `--standalone` on every turn. The turn runs against a private server instead of the shared background service, so the run does not depend on a background `opencode` service. Provider variables set on the shared service with `opencode service set env` do not apply to a standalone turn; provide them in the process environment. See [Background service](https://opencode.ai/v2/docs/cli#background-service) in the OpenCode CLI docs.

The stream splits one response across several `text` parts, and the adapter concatenates them with no separator. The join inserts a line break before a part that opens a report label (`Conclusion:`, `Why:`, `Blockers:`, `Checks:`, `Notes:`, `Deferred:`), because the parser matches each label plain at column 0 and a glued label makes the whole block unparseable, so `raw` carries the response instead (issue #316). Every other part joins with no line break, so a part boundary inside a sentence, or before the reviewer's `Verdict:` line, keeps the text as the model wrote it. A model that writes a `Verdict:` line after prose without a line break of its own therefore yields `verdict: unknown`.

A non-zero OpenCode exit reports the exit code and the provider detail, and no stream text.
