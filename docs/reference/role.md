# Child dispatch

## Interactive child dispatch: `agent-loop role`

An interactive parent session (Claude Code, Codex, or any harness with shell access) can dispatch one child turn without spawning a headless orchestrator:

```bash
# First call initializes the run state and dispatches the worker.
agent-loop role dispatch \
  --role worker \
  --cwd /path/to/work-tree \
  --task "Implement the change." \
  --mode work-first \
  --parent-session "$CLAUDE_SESSION_ID" \
  --worker claude --reviewer agy \
  --prompt-file ./prompt.txt

# Later calls read the configuration from the state file.
agent-loop role dispatch --role reviewer --cwd /path/to/work-tree --prompt-file ./review.txt
```

Operations: `dispatch` (default), `finish`, `abort`, `extend`, `declare-pr`, `refresh-local`, `set-model`, `wait-checks`.

- The run state lives at a fixed path derived from the resolved `--cwd` (`<os tmpdir>/agent-loops/runs/<sha256 of cwd, shortened>/state.json`, with `state.lock` beside it). There is no `--state` flag; `AGENT_LOOP_RUNS_ROOT` overrides the root for tests only.
- `--no-copy-local-files` and `--copy-local-path <relative path>` are init fields that control the copy of local files into a linked `--cwd`. A later call that names another value is refused, like every other init field, and a refused init writes no state and spawns no child. The init envelope carries `localFiles: {"copied": [...], "skipped": [...]}` when the copy ran, and no such key otherwise. A later dispatch adds `localFilesDiffer: [{path, changed}]`; `changed` is `source`, `copy`, `both`, or `unknown`, and `unknown` never means no change. A worker or reviewer turn that changes a copied source inside its window adds `localSourceChangedInTurn: [path]`; the parent reports it under `open` and asks the user before a refresh, because the user or another process can cause the change. The copy rules, the refused paths, and the comparison are in [Local files in a linked work tree](harness-entry-points.md#local-files-in-a-linked-work-tree) and [Local files copied into the work tree](../orchestrator/local-files-copy.md).
- The init call reads the sparse checkout of a linked `--cwd`. It reports the result as `sparseCheckout: {enabled, skipWorktree}` when the setting is on or a tracked path carries the skip-worktree bit. `skipWorktree` names paths only, relative to the work tree root, at most 20, redacted like the other path fields. The key is absent for the main work tree, when the read finds neither, and when the read fails or passes its 10 second bound.
  - The runtime logs a warning for a failed read, so an absent key proves nothing.
  - The read changes neither the setting nor a skip-worktree bit.
  - A linked work tree can inherit the main work tree's exclusion when `extensions.worktreeConfig` is on. The parent then disables it before the first dispatch, as [Work tree setup details](../orchestrator/work-tree-setup.md) states.
- `role dispatch` locks a linked `--cwd` at init, with the Git work tree lock reason `agent-loop run <id> active`. A plain `git worktree remove`, a single `--force`, and `git worktree prune` refuse that work tree. An existing lock of another owner is kept, and only a lock whose reason names this run is unlocked. Init in the main work tree succeeds with no lock and a log line.
- A terminal lifecycle unlocks the work tree: `finished`, `aborted`, and `halted`. An active, dispatched, or interrupted run keeps the lock. A later `finish` or `abort` on a terminal run releases a lock whose reason names the run, and keeps any other lock. A lock or unlock that fails prints a warning and never fails the command. The headless `agent-loop` command takes no work tree lock.
- The init call requires `--parent-session`, so a run through `role` is always guarded, and the headless `agent-loop` command is the explicit unguarded path. The refusals of a missing id and of an unexpanded placeholder are in [ADR 0006](https://github.com/andromarces/agent-loops/blob/main/adr/0006-require-parent-session-for-interactive-runs.md).
- The init call registers one session entry per run under `<root>/session-runs/<parent-session>/`, so a parent guard hook (#57) can look a run up by session id even when `--cwd` is a different work tree, and one parent session can drive several runs at once. The entry layout and the legacy `<root>/sessions/<parent-session>` file are in [Parent guard details](parent-guard.md).
- `role dispatch` blocks until the child turn ends and prints one envelope, so read each envelope before the next dispatch. The rules for several loops from one parent session are in [Several runs at once](../orchestrator-instructions.md#several-runs-at-once).
- A reviewer dispatch envelope carries `inheritedTmpdirEntries` only when entries appeared directly in the inherited temporary directory during the turn, and a reviewer or worker dispatch envelope carries it when entries appeared directly in a literal system temporary directory that differs from the inherited one. A worker turn reports only the literal directories, because it may legitimately write in the inherited one; when that directory is itself a literal root, a new entry there is reported too, because the two writes cannot be told apart (ADR 0095, ADR 0108). It is the diagnostic of one post-turn read, redacted and capped at 20, with no re-read or wait. It creates no `open` item by itself and never refuses a finish. A name with the `literal-tmp/` prefix is an entry of a literal system temporary directory, such as `/tmp/x` on macOS, or, for a worker turn, an entry of the inherited directory when it is a literal root: the prompt forbids the first write, the entry is unattributed, and the parent deletes nothing. A name with the `registered/` prefix is very likely the turn directory of a concurrent run, but the prefix is only a hint. An entry that a turn explicitly reports as its own leftover stays actionable, and the parent reports it under `open`. A runtime cleanup failure appears only in the runtime warning, which names the directory to delete by hand: the warning goes to the operator, and the parent adds no `open` item for it. The parent never deletes an entry that the field names.
- `--task-file <path|->` replaces `--task` on the init call. `--task` and `--task-file` cannot be combined, and an empty file is refused. The stdin form, the staging rules, and the rules for a later dispatch are in [Starting a run](../orchestrator-instructions.md#starting-a-run) and [Task delivery](../orchestrator/task-delivery.md).
- Prompts come from stdin by default, or `--prompt-file`. `finish` reads the summary as JSON on stdin, with five required keys and an optional `notes` key. `abort` takes `--reason`. `abort` on a `dispatched` run does the recovery steps of the interrupted transition first. It removes the turn directory that the dead dispatch kept, under every check of the removal. It appends the charged turn to `turns` as `interrupted`, then ends the run `aborted` (issue #1591, ADR 0088).
- `extend --max-steps <count> --parent-session <id> [--cwd <dir>]` raises the step budget of a non-terminal run in place, so the stored role session ids and first-turn tracking keep working. The caller must pass the stored `--parent-session` id. Every change is appended to `budgetChanges` as `{from, to, stepsUsed, at}` (ADR 0014). A child role of the run is refused through the `AGENT_LOOP_SPAWNED_RUN` marker that the runtime sets in the environment of every worker and reviewer process (issues #392 and #548, ADR 0014 point 8). The refusal rules, the limits of the id check and of the marker, and the unguarded run of a resumed session (issue #435, ADR 0021) are in [Blockers and terminal states](../orchestrator-instructions.md#blockers-and-terminal-states) and [Recovery after compaction or restart](../orchestrator-instructions.md#recovery-after-compaction-or-restart).

- `declare-pr --pr <pr> --parent-session <id> [--cwd <dir>]` sets `pr` once on a non-terminal run that declared none at init, for a task whose worker opens the pull request. After it the run behaves as one that passed `--pr` at init. The refusals, the envelope, and the follow-up steps are in [Declaring a PR run](../orchestrator/pr-declaration.md) (ADR 0041).
- `refresh-local --path <relative path> --parent-session <id> [--cwd <dir>]` records a hand refresh of one copied local file on a non-terminal run. It writes the source bytes over the run copy and stores their hash, so later dispatches stop reporting the path until a side changes again. The path must be one that init copied, with a stored hash, and the copy must still equal that hash. It refuses a missing or unreadable side, a link at the file or a parent component, a terminal run, and a child role. The copy keeps its prior mode, including the read-only attribute on Windows. The envelope is `{status, lifecycle, path}`, with no content and no hash.
- `set-model (--worker-model <model> | --reviewer-model <model>) --parent-session <id> [--cwd <dir>]` replaces the model of one role that has completed no turn, so a model that the CLI refused on the first turn of that role is repaired on the same run, where `abort` and a new run start every role on a new session (issue #1254, ADR 0070). A first Codex turn that a recognized model refusal ends charges no step, and its envelope carries `refusedModel` (issue #1565, ADR 0084). Exactly one model flag is required, and the role is the one it names. Only an `active` run takes it: a `dispatched`, `interrupted`, or terminal run is refused. A role with an `ok` turn in `turns`, a role the run did not configure, and a run with no turn history are refused, and so is an OpenCode model that holds a variant while the stored effort is set. A refused call changes nothing.
  - The step count and turn history stay, and the stored session id stays where the role kept one. The runtime side is tested with fake adapters: the next dispatch hands the adapter the kept session id and the new model. The adapter side is read from source, and a mocked-argv test holds a stored session id and a model together only for agy (`--conversation` and `--model`) and Copilot (`--session-id` and `--model`). The Claude Code (`--resume` and `--model`), Codex (`exec resume` and `-m`), and OpenCode (`--session` and `--model`) tests hold the session id and the model apart.
  - A request that names the current model of the role succeeds with `previousModel` equal to `model`, and it appends no entry and writes no state (issue #1274). Every change is appended to `modelChanges` as `{role, from, to, at}`, and the envelope is `{status, lifecycle, role, model, previousModel}`.
  - The caller must pass the stored `--parent-session` id, and a child role of the run is refused through the `AGENT_LOOP_SPAWNED_RUN` marker, as for `extend`. Any other call keeps rejecting a changed `--worker-model` or `--reviewer-model`.
  - The runtime does not probe a model at init: a probe costs one child turn for each role, and each CLI words its refusal in its own way.

  - The live check in issue #710 recorded a result for the five CLIs. Claude Code 2.1.316 and codex-cli 0.167.0-alpha.3 resumed the kept session on the new model.
  - Copilot CLI 1.0.106-2, opencode v0.0.0-dev-481, and agy 1.4.12 kept no session id after the refused turn. Their next turn started a new conversation.
  - OpenCode printed `"sessionID":""` on the refused turn.
  - The executed model is not verified for agy, because its JSON output has no model field.

- `wait-checks --pr <pr> [--all [--expect <check name>]...] [--head <sha>] [--cwd <dir>] [--timeout <seconds>]` waits for the required checks of that pull request. It prints one JSON envelope whose `head` names the commit that `checks` describe. It reads status only, writes no run state, needs no init, and returns inside its own bound. A pass is never read from an unresolved read, a `timedOut: true` envelope, or an envelope that carries `prFailures`. The full contract is in [`wait-checks`](#wait-checks).
- The state file records `task`, `mode`, `cwd`, `parentSession`, `maxSteps`, `timeout`, `stepsUsed`, `lifecycle`, `pr` (the declared run PR, or `null`), `turnsComplete` (present only on a run initialized by this version), `roles.{worker,reviewer}.{kind,model,effort,sessionId}` (`roles.worker` is null in `review-only`), `lastDispatch` (with `turnTmpdir`, the private temporary directory and child pid of an adapter turn), and `lastResult`, plus `budgetChanges` after an `extend`, `modelChanges` after a `set-model`, `summary` or `reason` when terminal, `unresolvedCompare` when a finished run recorded an unresolved PR-head compare, `noRequiredChecks` when a gated finish passed on a base branch with no required check, and `resumeDecision` when a maintainer resumed an interrupted run. Updates are atomic (temp file plus rename); exclusive access uses `state.lock` with a stale-lock check on the owner pid.
- Every run keeps a turn history without `--transcript`: `turns` holds one entry per dispatched turn, in order, each with `role`, `status`, `verdict`, `head`, and `at`, and report and response text stay out. A first turn that a recognized model refusal ends charges no step but still records its entry (issue #1565, ADR 0084). The entry shape, the `interrupted` status, the size bound, and the accepted `--max-steps` range (1 to 9007199254740991, `Number.MAX_SAFE_INTEGER`) with its re-check at `dispatch`, `finish`, and `extend` are in [Turn history and the step budget](../orchestrator/run-history.md).

- Lifecycle values: `active`, `dispatched`, `interrupted`, `halted`, `finished`, `aborted` (terminal: `halted`, `finished`, `aborted`). A turn interrupted between the CLI start and the state write leaves `dispatched` with a dead lock owner; the first call after the crash marks it `interrupted`, exits non-zero, and never repeats the turn, even with `--resume-interrupted`. From `interrupted`, only `abort` or an explicit `dispatch --resume-interrupted` is accepted. `--resume-interrupted` refuses while a live process holds the session of the dispatched Claude role. The refusal, its timing, the retry, and the unreadable process table are in [ADR 0031](https://github.com/andromarces/agent-loops/blob/main/adr/0031-refuse-continue-from-and-resume-interrupted-while-a-live-process-holds-a-claude-session.md) and [ADR 0032](https://github.com/andromarces/agent-loops/blob/main/adr/0032-detect-a-live-session-holder-on-interactive-init.md).
- The lock is fail-closed on ambiguity: a contender that finds a lock it cannot read, or whose owner has not finished writing it, exits non-zero and never removes it. Only a lock whose owner reads as dead, or an unparseable lock that no writer can own, is stale. One contender removes it under a claim file `state.lock.reap.<digest>`, a fixed-length name keyed by the SHA-256 of the guarded file name and its stale content, and only if the lock still holds the content that was read as stale, so a lock that a new owner created in between survives. A chain of more than two crashed claims fails closed. Lock creation is an atomic hard link, with an exclusive-create fallback on file systems that have none (FAT/exFAT, some network mounts).
  - The owner is a pid plus a platform start-time stamp (issue #498), so a reused pid reads as a new owner. Reading the stamp costs one `powershell.exe` startup on Windows. The measurement is in [ADR 0020](https://github.com/andromarces/agent-loops/blob/main/adr/0020-remove-orphan-claim-files-with-a-writer-liveness-check.md#windows-start-time-stamp-measurement) (issues #511 and #709). A cold start after a reboot and an idle host are not verified.
  - The orphan-claim removal (issue #452), the stamp forms, the PID namespace rule, and the limits are in [ADR 0020](https://github.com/andromarces/agent-loops/blob/main/adr/0020-remove-orphan-claim-files-with-a-writer-liveness-check.md).

- The reviewer turn runs under the same `withMutationCheck` as the headless loop: a detected mutation or snapshot error is fatal, keeps the charged step, and sets `halted`. No further dispatch is possible; the next run needs a new init call, which archives the halted file as `state.<timestamp>.json`.
- An init call is refused while a live process holds a Claude role session that the current or an archived state file of the work tree records. The match rule, the refusal, the unreadable process table, and the headless gap are in [ADR 0032](https://github.com/andromarces/agent-loops/blob/main/adr/0032-detect-a-live-session-holder-on-interactive-init.md).
- `mode: review-only` rejects `--role worker` as a hard guard and does not require `--worker` at init. `finish` is completion of the requested work, not code acceptance, and it is accepted from `active` in any mode. The review-only completion rules and the finish summary with an optional notes key are in [Completion](../orchestrator-instructions.md#completion) and [Finish output](../orchestrator/finish-output.md).
- `--mode <mode>` on the headless `agent-loop` command names the same three values the `agent-loop role` init call takes, and `--mode review-only` takes none of `--pr`, `--require-accept`, and `--require-ci`. The loop policy is in [Loop policy](../orchestrator-instructions.md#loop-policy), and the headless behavior, the refusal wording, and the transcript fields (issue #337) are in [Usage](usage.md).

- `--pr <pr>` on the init call declares that the run's work is delivered on that pull request, so the run can only end through the `--require-ci <pr>` gate for the same PR. A private GitHub Free-plan repository still refuses a declared run, so it must omit `--pr`. `--pr` is an init field that a later call cannot change, except `declare-pr`. The refusals, the base branch with no required check, and the accepted gap of a run with no declared PR (issues #286, #302) are in [Declaring a PR run](../orchestrator/pr-declaration.md).

- `--test-cmd <command>` and `--test-cmd-timeout <seconds>` on the init call make the runtime run the command in `--cwd` before each reviewer dispatch, outside the reviewer sandbox, and put the result in the reviewer prompt, in the envelope as `testRun`, and in `lastResult` in the state file. Pass the same `--test-cmd` on every reviewer dispatch: a changed or missing value is refused before a step is charged. The command runs inside a machine-wide test slot ([ADR 0040](https://github.com/andromarces/agent-loops/blob/main/adr/0040-run-the-test-command-in-a-test-slot.md)), and a `slot-timeout` is neither a pass nor a failure. The approved orphan-process limit is in [ADR 0017](https://github.com/andromarces/agent-loops/blob/main/adr/0017-run-a-test-command-before-each-reviewer-turn.md). The result fields, timeouts, cancel handling, redaction, and work-tree reporting are in [Reviewer prompts and runtime evidence](../orchestrator/reviewer-evidence.md#the-runtime-supplies-a-test-command-result).

- `--reviewer-sandbox read-only|workspace-write` on the init call sets the sandbox of each Codex reviewer dispatch ([ADR 0038](https://github.com/andromarces/agent-loops/blob/main/adr/0038-run-the-codex-reviewer-with-no-sandbox-by-default.md), which partially supersedes [ADR 0019](https://github.com/andromarces/agent-loops/blob/main/adr/0019-opt-in-workspace-write-sandbox-for-the-codex-reviewer.md)). `--reviewer-workspace-write` stays as an alias of `--reviewer-sandbox workspace-write`. The flag needs `--reviewer codex`, and any other reviewer is refused at init before a state file is written. The modes, the stored `reviewerSandbox` field, and its refusals are in [Codex reviewer sandbox mode](../orchestrator/reviewer-sandbox.md) and [Turn history and the step budget](../orchestrator/run-history.md).
- Two opt-in finish gates apply to `work-first` and `review-first`: `--require-accept` and `--require-ci <pr>`. Each refusal names the failed condition. In `review-only`, a flagless `finish` keeps the current behavior and each gate fails with a clear error. The conditions, their refusal order, the absence rule, and the no-required-check pass (`noRequiredChecks`, issue #336) are in [Finish gates](../orchestrator/finish-gates.md#finish-gates). The classes of source replies are in [ADR 0012](https://github.com/andromarces/agent-loops/blob/main/adr/0012-establish-the-absence-of-a-required-check.md).

- Live verification of the classic-protection absent-check refusal with a non-admin `GITHUB_TOKEN` is recorded in [PR #285](https://github.com/andromarces/agent-loops/pull/285). The disposable probe repository was deleted after [issue #296](https://github.com/andromarces/agent-loops/issues/296); the recorded result does not depend on it.
- The reviewer prompt carries a fixed review scope on every turn, which sets what a blocker is (issue #1073).
  - The scope also bars contact with a host or service that the task does not name. GitHub reads that the rules allow stay allowed. A local process or loopback server that a check starts stays allowed (issue #1522).
  - When the task names a pull request, that prompt also carries a required-check read (issues #313 and #317).
  - `--require-ci` still enforces that read (issues #313 and #317).
- A run that declares `--pr` also gets a runtime-read advisory status before each reviewer turn (issues #320, #349, and #350).
- A required check that is still pending after a wait is not a finish condition (issue #319).
- The wait is a status read that changes nothing.
  - A status read is not a review, not a test, and not an edit.
  - It is one exception to the orchestrator role rule, and `agent-loop role wait-checks` is the only command it covers (issue #348).
- The rules are in [Reviewer prompts and runtime evidence](../orchestrator/reviewer-evidence.md) and [Waiting for required checks](../orchestrator/waiting-for-checks.md).
  - The headless wait command and its limits are in [ADR 0013](https://github.com/andromarces/agent-loops/blob/main/adr/0013-bound-the-headless-required-check-wait.md).

- The reviewer closing block tells the reviewer to state each blocker concretely in the `Blockers` line and never to point at text outside the block, for example "the defects above". The parent reads only the closing block, so a pointer leaves the worker without the defect (issue #434). The block keeps its one-line, no-list format.
- The worker first-turn prompt has the same rule for every result the parent needs, such as findings, drafts, decisions, and open questions: each stands in full inside the closing block, and the worker never points at text outside it, for example "the decisions above" (issue #976).
- The worker first-turn prompt bars an unbounded CI wait, such as `gh pr checks --watch` (issue #1459). The run waits for the required checks outside the worker turn with `agent-loop role wait-checks`, where the run permits it. A worker that reads CI uses a bounded read.
- The worker first-turn prompt states that a suite which cannot finish in the foreground ends with the local suite reported as not run in `Checks` and the required CI checks as the evidence (issue #1530). A worker never ends the turn while a command it started is still running, and never moves the suite to the background.
- The worker first-turn prompt bars contact with a host or service that the task does not name, unless the task names it (issue #1522). A local process or loopback server that a check starts stays allowed. A check that needs a host or service goes in Checks as unverified and in Deferred.
- The worker prompt keeps the full output of a commit or push hook, or its failing and summary lines. It reports the hook result in Checks. It never pipes `git commit` or `git push` through a filter that cuts the output (issue #1533).
- The worker later-turn prompt states that `TMPDIR` names a new private directory on every turn, so the worker reads it again and never reuses a temporary path from an earlier turn (issue #1610). A later turn resumes the same session and gets no preamble, so this rule reaches it.
- The worker first-turn prompt names a repository hook that starts a test command (issue #1602). A `pre-push` or `pre-commit` hook under `core.hooksPath` or `.git/hooks` runs outside the test slot. The worker runs such a `git push` or `git commit` through the plain test slot wrapper. The hook suite then holds a machine-wide slot.
- The worker first-turn prompt states the red-run rule (issue #1612). A red run of one or a few test files that must fail before the fix is a targeted run through the test slot wrapper with `--if-held`. Its wait stays below the shell tool bound. A red run that the wrapper does not start goes in `Checks` as not run with the reason and in `Blockers`, and the worker never implements the fix first and restores the old source to stand in for it. A path whose wrapper command cannot be quoted keeps the direct targeted run of the same fallback, under the same 10-file bound ([ADR 0096](https://github.com/andromarces/agent-loops/blob/main/adr/0096-wait-for-a-held-slot-in-a-bounded-red-run-and-report-a-miss.md)).
- The worker first-turn prompt states the work tree edit rule (issue #1494). Edit, create, and delete files only under the run work tree. Before an edit with an absolute path, check that the path starts with the work tree root. A path that a tool returns for another checkout maps to the same relative path in the run work tree.
- The worker first-turn prompt states the report-and-stop rule (issue #1551). If an edit lands in another checkout, report the paths in the closing block and stop. Never restore or discard a file there, because a restore can discard an uncommitted change of the user.
- The worker prompt states on the first and every later turn that the reasons belong under `Why:`, never under another heading such as `Verification:` (issues #1601 and #1613).
- The reviewer is required to end with one explicit `Verdict:` line (`accept` or `reject`, parsed case-insensitively) inside its closing block. The verdict word alone, the word closed by a sentence period (`reject.`), or the word followed by a separator and a trailing clause (`reject — the state does not pass`) parses to that word, unless the clause names either verdict as a whole word. Any other malformed value, including a missing line or a line that names both verdicts, yields `verdict: unknown`; process success never implies acceptance.
- `--transcript <file>` appends one JSON line per `invocation` and `result` event, in the same shape as the headless mode, accumulating across calls. It stays a per-call flag; the `turns` array above is the history every run keeps without it.

Stdout carries exactly one JSON envelope, except for `role --help` and `role -h`, which print plain usage text and exit 0. All logs go to stderr.

A string error message prints unchanged. A message of `null` or `undefined` is not serialized. The error is then the text of the whole error value, for example `Error: null` for an `Error` and `[object Object]` for a plain object. Outside a handled child error, any other message value serializes once under the key `error`, exactly as the envelope serialized it before. Its JSON type and its `toJSON` redaction are kept, and a state file that records the result holds the same value. A message that serializes to `null`, such as `NaN`, `Infinity`, or a `toJSON` that returns `null`, then prints JSON `null`.

A value that cannot serialize, or that serializes to nothing (a function, a Symbol, or a `toJSON` that returns `undefined`), prints a fixed text instead. The fixed text is `[unserializable message]`, or the digits of a BigInt. The envelope therefore never fails to stringify, and an error envelope always carries `error`.

A handled child error result carries text, not a JSON value. A non-string value that the serialization yields prints as its JSON text, so `null` prints the string `"null"`. A string value, such as one that a `toJSON` returns, prints unchanged. A handled child error that timed out prints `<role> timed out after <seconds> seconds` instead of its message.

A message that throws when read prints `Unreadable error`, except for a handled child error that timed out. Before the child turn starts, a message that throws a canceled error prints `Interrupted by SIGINT` instead. Only a message that throws after the child turn starts ends with a recorded result in the state file.

If the stdout write itself fails, for example on a closed pipe, no envelope can be delivered. The command then writes `Failed to write the envelope to stdout: <code>` to stderr. It exits 1 when the command outcome was exit 0, otherwise it keeps that non-zero exit code:

```json
{
  "role": "reviewer",
  "status": "ok",
  "report": {
    "conclusion": "...",
    "why": "...",
    "blockers": "...",
    "checks": "...",
    "notes": "...",
    "deferred": "..."
  },
  "verdict": "accept",
  "reviewed": {
    "head": "...",
    "clean": true,
    "exact": true,
    "digest": "..."
  }
}
```

`report` is parsed from the closing block every child turn must end with. `conclusion`, `why`, and `blockers` are required; `checks` (the commands that ran and their results), `notes` (non-blocking findings), and `deferred` (out-of-scope items) are optional, and an omitted or empty label yields `null` for that field without making `report` null. Every child turn is asked for a `Checks` line, for a worker turn and a reviewer turn alike (issue #310), but only the reviewer `Checks` line is a gate input, so a worker `Checks` line is reported evidence and never an accept. Each label takes one line, plain at column 0.

The closing-block list rules fold a `- ` or ordered list under a report label into that label's value, and any other list shape makes the block unparseable. The full rules are in [Closing block list rules](../orchestrator/closing-block.md). A successful child response whose block parses to null takes one repair turn in the same session, asked for the block alone; the step stays charged, and the repaired report replaces the null one only when it keeps the original label values and an explicit original verdict (issue #1615, ADR 0094). When the repair does not run or also parses to null, `report` is null and `raw` carries the original response. A missing required label adds `reportMissingLabels`, which names each missing label, for example `["Why"]`. It holds no response text. A report that parses but lacks the reviewer `Checks` line or `Verdict` line takes no repair, and the existing acceptance refusal stays.

A child turn whose adapter returns a missing or non-string response ends `status: "error"`. The error names the missing string response, never `ok` with `report: null`. `status: "error"` carries `error`, and every error path still prints one JSON object. The subcommand launches no orchestrator model and accepts no `--orchestrator` flags.

A Codex error envelope can carry `refusedModel`, the model that the CLI refused, for example `"refusedModel": "gpt-6.1"`. The error text names the refusal. A recognized refusal on the first turn of the role charges no step and still records its `turns` entry, so the parent can run `set-model` and dispatch again inside the same budget (issue #1565, ADR 0084). A refusal on a later turn charges a step as before.

A reviewer envelope carries `reviewed`: `{ head, clean, exact, digest }` from the snapshot the runtime takes before the reviewer turn, so the child cannot misreport it. A reviewer turn in a run that named a PR also carries the advisory `prChecks` status that the runtime read for that PR head, and the state file keeps it in `lastResult`. The fields, the `unresolved` cases, and the rule that a run with no PR carries none are in [Reviewer prompts and runtime evidence](../orchestrator/reviewer-evidence.md#the-runtime-supplies-the-required-check-status) (issues #320 and #350).

`head` is the commit, `clean` is true when the work tree has no uncommitted entries, `exact` is true when every entry has a content hash or is a deletion, and `digest` identifies the uncommitted state. A symlink hashes its link target text with a tag, so two links with different targets have different digests, dangling included, and a link never collides with a regular file that holds the same bytes.

The `finish` envelope is `{ "status": "ok", "lifecycle": "finished" }`, and the command exits 0. A finish that recorded an unresolved PR-head compare adds `"unresolvedCompare": true`, and a verified `finish --compare-head <pr>` adds `"headCompare": "verified"` (#1098, #1021). The summary keys, the marker, and the `--compare-head` guards are in [Finish output](../orchestrator/finish-output.md).

## `wait-checks`

Part of [Child dispatch](#interactive-child-dispatch-agent-loop-role). The orchestrator rules for the command are in [Waiting for required checks](../orchestrator/waiting-for-checks.md), which also holds the retry, paging, and `Link` host rules of its reads.

Usage: `agent-loop role wait-checks --pr <pr> [--all [--expect <check name>]...] [--head <sha>] [--cwd <dir>] [--timeout <seconds>]`. It prints `{"status": "ok", "pr": 42, "timedOut": false, "head": "<sha>", "checks": [{"name": "ci", "state": "SUCCESS", "bucket": "pass"}]}`.

The [wait rules](../orchestrator/waiting-for-checks.md#waiting-for-required-checks) hold each rule that this page previously restated.

`--cwd` must be inside a Git work tree, as it is for `dispatch`.
